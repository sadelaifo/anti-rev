# antirev

Binary protection system that encrypts executables and shared libraries, then runs them from memory (memfd) to prevent reverse engineering. Key components:

- **stub**: C launcher that decrypts bundled binaries into memfds and executes via `fexecve`
- **antirev_shim**: the single LD_PRELOAD shim — one `.so` per arch (`antirev_shim_x86_64.so`, `antirev_shim_aarch64.so`). Bundles every interceptor into one DSO so the stub only writes one memfd and adds one entry to `LD_PRELOAD`. Sources:
    - `stub/exe_shim.c` — `readlink` / `realpath` / `getauxval` identity hide
    - `stub/dlopen_shim.c` — `dlopen()` redirect to `/proc/self/fd/N` (eager via `__r_FM`, lazy via daemon `OP_GET_CLOSURE`)
    - `stub/aarch64_extend_shim.c` — aarch64-only, compiled as an empty TU on x86: `ANTI_LoadProcess(struct ANTI_ProcessInfo *)` hijack + `popen`/`pclose` workaround (glibc's vfork-based popen corrupts memfd-heavy parent processes on this arch). CMake conditionally adds the file to `antirev_shim` sources only on aarch64; x86 builds don't pull in any of its code.
    - `stub/daemon_client.c` — shared daemon-protocol client owning the socket fd (`__r_LS`), the eager fd map (`__r_FM`), and the encrypted-name set (`__r_EL`). Both `dlopen_shim` and `aarch64_extend_shim` talk to the daemon through `daemon_client_send` / `daemon_client_recv` and check encryption / eager-lookup state through accessors instead of carrying private copies. Init is idempotent — each shim's constructor calls `daemon_client_init()` and only the first call reads env vars.

    Each source file keeps its own concern (identity, dlopen, ARM-only, daemon transport) with disjoint symbol exports and independent file-scope state where it makes sense to stay isolated (per-shim caches, mutexes, log files).
- **encryptor** (`protect.py`, `antirev-pack.py`): Python tools that encrypt and bundle binaries with AES-256-GCM
- **daemon mode** (`lrxd`): a lightweight lib-server process that scans `$HOME/SA` (the suite's install tree; falls back to its own directory when `$HOME/SA` is absent) for encrypted `.so` / `.elf` files, decrypts them into memfds, and serves the fds to client processes via SCM_RIGHTS.  Pinning the scan root to `$HOME/SA` lets the daemon live in a subdir (e.g. `$HOME/SA/bin`) while still serving libs from the whole tree (e.g. `$HOME/SA/lib`).  (Filename was `.antirev-libd` historically, then `.lrxd`; the leading dot was dropped because a hidden *executable* is itself a red flag, and dotfiles get skipped by glob/rsync copies — plain `lrxd` blends in with ordinary binaries and copies cleanly. Multi-arch deploys get `lrxd-x86_64` / `lrxd-aarch64`.)
- **antirev_client.py**: Python client that connects to the daemon, receives decrypted lib memfds via SCM_RIGHTS, and patches `import` + `ctypes.CDLL` to transparently load encrypted libs. Handles dependency ordering via `_ensure_loaded()` which recursively preloads transitive DT_NEEDED deps with `RTLD_GLOBAL`.
- **build.py**: compiles/obfuscates Python source files via Cython, Nuitka, or PyArmor

## Target environment

This project protects a business software suite consisting of:
- 100+ executables
- 550+ shared libraries
- 1000+ Python scripts (some of which dlopen encrypted .so files)

The business software also uses third-party libraries (e.g. `libdopra.so`, `libprotobuf.so`, open62541, Boost) which are NOT encrypted but coexist in the same processes.

## Architecture notes

- Protected binaries run from memfd via `fexecve`. `/proc/self/exe` points to `memfd:<random-hex> (deleted)`.
- **Per-process random memfd name**: every memfd created by the stub or daemon (`make_memfd` in `stub.c`) shares a single name lazily derived from `/dev/urandom` on first use — 6 random bytes encoded as 12 hex chars. The protected exe, every daemon-decrypted lib, and the embedded `antirev_shim` blob all get the same name within one process, so `ls -la /proc/<pid>/fd/` and `cat /proc/<pid>/maps` can't tell which fd holds which encrypted artifact. Different processes get different names, so an attacker can't grep `/proc` for a fixed project marker across hosts. The kernel-prepended `"memfd:"` prefix is unchanged, so the shims' owner-process probe (`strstr(exe_buf, "memfd:")`) keeps working. Fallback when `/dev/urandom` is unavailable: `"x<pid>"` — kept short and non-revealing. Note: this is defense against external observation only — anyone who can `cat /proc/<pid>/fd/N` reads the decrypted ELF regardless of its name and can recover SONAME / symbols from the bytes themselves. Verified by `test_memfd_name`.
- The exe_shim constructor may run after C++ global static initializers in DT_NEEDED libraries. On x86_64, `is_owner_process()` handles this via lazy detection — the first interceptor call re-probes `/proc/self/exe` for `memfd:` and sets `g_owner_pid` on its own. On aarch64 the lazy path is compiled out; ownership is decided only inside the constructor (matching master's field-tested ARM behavior).
- Child processes inherit `LD_PRELOAD` but the shims detect non-owner processes (by checking `/proc/self/exe` for memfd) and pass through to real libc functions.
- **Owner-side env scrub (aarch64 only)**: on ARM the constructor also strips `/proc/self/fd/*` out of `LD_PRELOAD`, `/tmp/antirev_*` out of `LD_LIBRARY_PATH`, and unsets `__r_FM` even inside the owner process. The shims are already mapped, so env entries are only load-bearing for children spawned via `popen`/`system`/`fork+exec`; on ARM the business stack closes random fds and those children fail to start if they inherit `/proc/self/fd/N` preloads. x86_64 deliberately skips this scrub — its test matrix includes a protected parent forking a plain child that dlopens an encrypted lib through the daemon (see `test_fork_same_lib`), which requires the child to inherit `__r_FM` + the shim `LD_PRELOAD`.
- The daemon mode splits libs into DT_NEEDED (resolved via symlink dir on `LD_LIBRARY_PATH`) and dlopen'd (lazy, fetched on demand). DT_NEEDED libs are NOT on `LD_PRELOAD` — glibc's normal BFS resolves them through the symlink dir, preserving the original symbol lookup order. `LD_PRELOAD` contains only `antirev_shim` (one entry, both arches).
- **Symlink dir lifecycle**: each protected exe creates `/tmp/antirev_<pid>_XXXXXX` via `mkdtemp` in Phase 4c (the `<pid>` tag encodes ownership). Cleanup is two-tiered:
    - **Normal exit** — `exe_shim`'s ctor captures `__r_SD` into a static buffer and registers `atexit(cleanup_symlink_dir)`. Because `exe_shim`'s ctor runs very early and atexit is LIFO, the cleanup fires very late, after most shutdown work that might still walk the dir. Guarded by `is_owner_process()` so forked-non-execve children don't try to delete the parent's dir.
    - **Crash** (`SIGKILL`/segfault/`_exit`) — the daemon's `sweep_dead_symlink_dirs` walks `/tmp` at daemon startup and during clean shutdown, parses the `<pid>` out of each `antirev_<pid>_<rand>` name, and `rm -rf`s any whose owner PID is dead (`kill(pid, 0) == ESRCH`). Legacy no-PID names (created by old code paths) are skipped — without a PID we can't decide ownership safely.
    - **Python parallel**: `antirev_client.py` mirrors both halves — `tempfile.mkdtemp(prefix="antirev_<pid>_")` so the daemon reaper recognizes its dirs, plus `atexit.register(_cleanup_link_dir)` for normal exit.
- `antirev-pack.py` computes per-exe transitive DT_NEEDED using topological sort (Kahn's algorithm) to embed the needed-libs section. The stub uses this to create symlinks for the correct set of libs.
- **DT_NEEDED fd cleanup**: after glibc's dynamic linker has mapped the DT_NEEDED libs, their backing memfds are pure bookkeeping — the mappings keep the memfds alive. The stub passes the fd list via `__r_CF=n,m,...` and `exe_shim`'s constructor closes each one, freeing fd-table slots so that later `socket()`/`open()` land at low fd numbers. Matters for any code that still uses `select()` (FD_SETSIZE=1024).
- **Lazy dlopen fetch (Mode C daemon path)**: the stub only eagerly fetches the exe's encrypted DT_NEEDED set (filtered through `all_enc_names` from `OP_LIST`). The Unix socket to the daemon is kept open across `fexecve` and passed to the child via `__r_LS=<fd>`. `dlopen_shim` inherits `__r_EL` (comma-separated) and `__r_SD`; on each `dlopen()` of an encrypted basename it sends `OP_GET_CLOSURE` to fetch the lib plus its transitive encrypted DT_NEEDED closure in one round trip, materializes symlinks in the shared dir, then calls `real_dlopen` (glibc resolves via `LD_LIBRARY_PATH`). Returned fds are cached for the process lifetime to pin `/proc/self/fd/N` paths — closing and reusing them would make glibc collapse different libs into one link-map entry. The daemon parses each lib's `.dynamic`/`DT_NEEDED` at startup via `build_deps_graph()` so `OP_GET_CLOSURE` is a graph lookup. New opcodes: `OP_LIST`/`OP_NAMES`, `OP_GET_CLOSURE` (replies reuse `OP_BATCH`/`OP_END`).
- **Preload-closure-deps on lazy fetch**: after receiving the closure, `dlopen_shim::fetch_closure` iterates it in topological (DFS post-order) order and calls `real_dlopen(symlink_path, RTLD_LAZY | RTLD_GLOBAL)` on every *non-root* entry before the caller's own `real_dlopen` of the root. `RTLD_GLOBAL` is mandatory — generated `.pb.cc` code exports `descriptor_table_<file>_2eproto` with default visibility, and duplicate definitions across plugins (common ODR-ish build pattern for protobuf) dedup via symbol interposition only when both DSOs are in the global scope. The root lib is explicitly skipped so the caller's own dlclose can actually unload it, which matters for plugin systems that cycle plugins carrying overlapping static state (see `test_dlopen_reload`, `test_dlopen_interpose`, `test_python_reload`).

### aarch64_extend_shim (aarch64-only)

Compiled into `antirev_shim.so` only on aarch64 (the source file is an empty TU on x86). Houses two unrelated aarch64-specific interceptors:

- **`ANTI_LoadProcess(struct ANTI_ProcessInfo *)` hijack**: business API that loads a program-binary `.elf` from the path in `info->ltrBin`. aarch64_extend_shim computes `basename(info->ltrBin)`, checks it against the shared `__r_EL` set (via `daemon_client_is_encrypted` — `.elf` and `.so` basenames coexist), and on match fetches the decrypted memfd from the daemon via **`OP_GET_LIB` (reused, no new opcode)**, rewrites `info->ltrBin = "/proc/self/fd/N"`, then calls the real `ANTI_LoadProcess` via `dlsym(RTLD_NEXT, ...)`. The rewrite is persistent — not restored on return — so deferred reads of `info->ltrBin` (worker threads, multi-stage loaders) still hit the memfd. `ANTI_UnLoadProcess(pgId)` is **not** intercepted — it keys on a pgId handle, not the path, and the kernel mapping created by the real `ANTI_LoadProcess` pins the memfd regardless of whether our fd cache stays open. The memfd fd is cached per pgName for the process lifetime.
- **`popen` / `pclose`**: moved verbatim from `exe_shim.c`. Rationale unchanged — glibc's vfork'd popen child corrupts the memfd-heavy parent; we override with plain fork+exec and maintain our own FILE*→pid table so `pclose` reaps the right child.

aarch64_extend_shim and `dlopen_shim` share the daemon socket via `daemon_client.c` — single `g_sock` for the whole DSO, accessed through `daemon_client_send` / `daemon_client_recv`. Both shims have their own mutex, so cross-shim requests hitting the socket concurrently from different threads could interleave responses — not an issue today because `ANTI_LoadProcess` is called at process init (single-threaded) while `dlopen` happens later, but worth noting if that timing ever changes.

Packing:

- **CLI path** (`protect-daemon --libs`): `.elf` files can be passed alongside `.so` files — daemon indexes them by basename, no separate flag.
- **YAML/`antirev-pack.py` path**: `classify_elf` treats any file whose basename ends in `.elf` as `kind='lib'` (regardless of ET_EXEC vs ET_DYN), so `.elf` PG binaries flow through the same encrypt/skip + `encrypt_libs` / `plaintext_libs` filters as `.so` libs. Without this, ET_EXEC `.elf` files would fall into the exe pipeline and get wrapped as standalone `.protected` stubs — wrong semantics for ANTI_LoadProcess targets. `_encrypt_lib_worker` skips the patchelf SONAME-patching step for `.elf` files (ANTI_LoadProcess targets are looked up by basename via `OP_GET_LIB`, never via DT_NEEDED, so no SONAME is needed).
- **Stub side**: `scan_encrypted_libs` in `stub.c` accepts both `.so` and `.elf` extensions as its fast-path filename filter — the authoritative check remains the `ANTREV01` magic header.
- **Unsupported-arch fallback**: when the YAML `stubs:` map omits an arch present in the install tree (e.g. only `aarch64` configured but x86_64 binaries appear), `antirev-pack.py` no longer hard-errors. The unmatched ELFs are copied to `output_dir` as plaintext with a per-arch `[pack] WARNING` summary listing each affected file. This keeps the install tree complete while flagging the omission so a typo in `stubs:` is still visible.

### aarch64_extend_shim env vars (runtime)

- `ANTIREV_AARCH64_EXTEND_LOG=<path>` — line-buffered log of every `ANTI_LoadProcess` call, path-rewrite decision, and daemon fetch outcome. Use this to diagnose "daemon returned no fd" or "basename not in enc list" issues in the field.

### dlopen_shim env vars (runtime)

- `ANTIREV_DLOPEN_LOG=<path>` — when set, `dlopen_shim` writes every `dlopen` decision, closure fetch, preload, and failure to `<path>` with line-buffered IO. Required for diagnosing any closure / preload issue in the field.
- `__r_NP=1` — escape hatch that disables the per-dep preload loop entirely. `fetch_closure` still fetches the closure and materializes symlinks, but the caller's `real_dlopen(root)` then triggers glibc's normal recursive DT_NEEDED walk, which maps every dep first and runs all ctors together at the end — matching plaintext semantics exactly. Use this for apps with **implicit inter-lib symbol dependencies**, where one business lib references a symbol provided by a sibling lib without an explicit `DT_NEEDED` edge (e.g. `_ZN3BBBC1EPN6google8protobuf5ArenaE` — `BBB::BBB(google::protobuf::Arena*)` — needed by libccc but provided by libbbb with no edge between them). The per-dep preload loop loads ctors in isolation and can trip lazy-binding failures across the implicit boundary; natural load sidesteps it. Tradeoff: without preload, any lib whose `DT_RPATH` points at the encrypted on-disk dir will have its own DT_NEEDED search hit ciphertext before `LD_LIBRARY_PATH` catches it — so `__r_NP` is opt-in per-app, set in the start script, not the default. The correct long-term fix is to add the missing `DT_NEEDED` edge to the business build (`target_link_libraries(CCC PRIVATE BBB)` in libccc's CMakeLists), which makes the dependency explicit and works for every loader.

### Python integration

Python scripts load encrypted libs via `antirev_client.py` — called from within Python (`from antirev_client import activate`). Connects to the daemon, patches `ctypes.CDLL` and `sys.meta_path` to redirect to memfd-backed libs. Loads encrypted libs with `RTLD_GLOBAL` and creates soname symlinks in a temp dir prepended to `LD_LIBRARY_PATH`. Speaks daemon protocol v2 — sends `OP_INIT` on connect and collects `OP_BATCH`/`OP_END` framed replies. Covered by `test_python_client_daemon`.

### Known issues with memfd loading

- Each decrypted lib holds an open memfd, consuming file descriptors. Large deployments (550+ libs) may require raising `ulimit -n`.
- The dynamic linker's path-based deduplication uses `l_name` from the load path. The same library accessed via memfd path (`/proc/self/fd/N`) vs disk path may be treated as different libraries.
- **Duplicate-symbol detection**: `tools/missing_syms.py` runs a per-target duplicate-symbol scan by default. For every project ELF it walks the transitive DT_NEEDED closure (plus the ELF itself) and reports symbols defined by more than one DSO in that load image. STRONG-vs-STRONG duplicates are errors (real interposition / ODR risk); WEAK-vs-WEAK and STRONG-vs-WEAK are warnings (common C++ vague linkage; usually benign but worth surfacing). C++ vague-linkage prefixes (`_ZTV`, `_ZTI`, `_ZTS`, `_ZTC`, `_ZTT`) are filtered by default — pass `--all-cxx` to include them. System-lib-only duplicates (e.g. libc vs ld-linux) are filtered unless `--system-dups` is given. Use `--no-duplicates` to skip this pass.
- Legacy binaries without the needed-section (backward compat) still use LD_PRELOAD for encrypted libs, which changes symbol lookup order. Re-pack with `antirev-pack.py` to get the symlink-dir-only approach.
- **Debug symbol files (.debug) affect runtime behavior**: exe_shim spoofs `readlink("/proc/self/exe")` to point to the encrypted stub on disk. Business software that scans for `.debug` files relative to the exe path (e.g., signal handlers, crash recovery) will find or miss them depending on deployment. Two encrypted processes (Foo, Bar) crash in open62541 `ua_client()` init when `.debug` files are absent, but work fine when present. A standalone demo (tests/opcua_enc/) confirmed encryption itself does NOT cause the crash — the issue is the business software's debug-file-dependent infrastructure. **Workaround**: always deploy `.debug` files alongside encrypted binaries. **Investigation pending**: strace to identify which library reads `.debug` at runtime.

## kmod2: antirevfs kernel module (experimental alternative architecture)

`kmod2/` is a self-contained, alternative architecture (see `kmod2/DESIGN.md`) that replaces the entire stub + shim + daemon + `antirev_client.py` stack with a stacked read-only kernel filesystem, **`antirevfs`**. It is NOT wired into the main CMake build or `run_all_tests.cmake` — it has its own kbuild Makefile and a standalone root-only test. It is a working PoC/v1, not the production path; the daemon/shim architecture above is still the shipping design.

- **What it does**: ciphertext lives under a lower `.enc/` tree; antirevfs mounts over it and decrypts `ANTREV01` AES-256-GCM files in `read_folio` (page-fault servicing). The kernel page cache gives cross-process page sharing for free — no daemon, no `LD_PRELOAD`, no `memfd:` artifact in `/proc/<pid>/maps`. glibc/`ld.so`/Python see plaintext at real paths, so the implicit-DT_NEEDED / ODR pain (`ANTIREV_NO_PRELOAD`) disappears with native symbol resolution.
- **On-disk format — embedded-key trailer (no mount-time key)**: `[magic ANTREV01:8][iv:12][tag:16][ct...][key:32][magic ANTREV01:8]`, produced by `antirev-fs-pack.py` or `protect.py encrypt-lib --embed-key` (via the shared `protect.make_container(data, key, embed_key=True)`). Unlike the keyless daemon/shim container, antirevfs embeds each file's AES key in a TRAILER (key + a second magic so the trailer is self-marking), mirroring the master-branch stub trailer. **There is no mount-time key, no keyring, no `key=`**: `read_folio` reads the key fresh from each file's trailer at decrypt time (never cached in inode/sb, stack copy `memzero_explicit`'d after use). Whole plaintext is one GCM message → one-shot whole-file decrypt into a per-inode buffer on first fault (tag verified once), then serves pages. plaintext_len = lower_size − HDR(36) − TRAILER(40). An **unauthorized** reader is served the file with the trailer **stripped** — a valid-looking but keyless, undecryptable `[magic][iv][tag][ct]` container (see `gate_passthrough_cipher`). Per-page random decrypt is impossible (GCM authenticates the whole message). **Tradeoff**: the key now lives inside each `.enc/` file, so a raw copy of the lower tree is decryptable — protection rests on the mount stripping the trailer for unauthorized readers + the `.enc/` tree staying namespace-isolated (master-branch posture). Hardening the embedded key is future work ([[project_key_obfuscation]]).
- **Module sources** (`kmod2/module/`): `super.c` (fs registration, `mount_nodev`, option parse, inode/sb lifecycle — **no key acquisition**: mounting is key-free), `inode.c` (lookup proxied to lower tree, `iget5_locked` caching keyed on lower dentry so one antirevfs inode == one shared page cache per path, getattr reporting plaintext size, and **symlink support** — `S_IFLNK` lower inodes get an `antirevfs_symlink_iops` whose `get_link` proxies to the lower link via `vfs_get_link`, so packer-mirrored SONAME chains / version links resolve through the mount; without this the module rejected every symlink with `-EINVAL` and they showed as `l?????????` / dangling), `file.c` (`read_folio` decrypt-on-fault, dir `iterate_shared`, normal file ops, plus the trailer-stripped passthrough ops for unauthorized readers), `crypto.c` (`gcm(aes)` via kernel crypto API; reads the per-file key from the trailer, then builds a `[ct||tag]` buffer for the AEAD since the file layout has tag *before* ct; `antirevfs_has_trailer` confirms the trailing magic), `antirevfs.h`.
- **Strict mode + passthrough + passdata**: a file under the mount lacking `ANTREV01` magic returns `-EIO` unless either (a) its extension is in the mount's `passthrough=` whitelist (colon-separated, since `,` separates mount options), or (b) the mount carries the `passdata` option, which serves **any** non-`ANTREV01` file as plaintext passthrough. Decided at inode-classify time (open of lower file to sniff magic). `passdata` is the mode for a **complete mixed-content read-only tree** (a real `lib/`/`bin/` holding encrypted ELFs *plus* `.py`/`.pyc`/`.sh`/`.txt`/`.json` data files *plus* third-party plaintext ELFs that coexist) — produced by `antirev-fs-pack.py` with `mirror_plaintext`. Encrypted (`ANTREV01`) files are still decrypted and gated as usual; only non-magic files become plaintext. Tradeoff vs the extension whitelist: `passdata` drops strict mode's "an unencrypted ELF that slipped past the packer is loud" net (a forgotten-to-encrypt `.so` would be served plaintext), so it relies on the packer's encrypt-all-ELF default + manifest review. The mount stays **read-only**: any file the app *writes* at runtime (python-generated `.txt`, `__pycache__`) must be redirected to a writable path outside the mount — antirevfs hosts only shipped content, and edits to `bin/`/`lib/` are intentionally impossible. Mount via `antirev-mount --passdata <lower> <mp>`.
- **Key — embedded per file, no mount-time key**: there is no `request_key`, no keyring, no `key=` option, and no session-keyring dance. Each encrypted file carries its AES key in its trailer; the module reads it at decrypt time (`crypto.c`, fresh per file, `memzero_explicit`'d). This deliberately deletes the old session-keyring gotcha (the `_ses` sharing problem that made it pass on 6.8.0-117 but fail on SLES 12 SP5) — there is simply no key to place in a keyring. `super.c`'s `antirevfs_fill_super` no longer acquires a key; `kill_sb` no longer wipes one. The tradeoff (lower tree contains keys) is covered in the on-disk-format bullet above.
- **Tools** (`kmod2/tools/`): `antirev-mount` (`mount -t antirevfs` wrapper, read-only view — key-free), `antirev-mount-rw` (writable view — see next bullet). `antirev-keyctl` is **deprecated** (no effect on a current mount — keys are per-file) and kept only for legacy flows. `dkms.conf` for auto-rebuild on kernel upgrade.
- **Writable view (`antirev-mount-rw`)**: a bare antirevfs mount is read-only three ways over (`SB_RDONLY` + no `write_folio` + dir iops carry no `.create`/`.unlink`/`.rename`), so any write returns `-EROFS`. Business software that writes lock/log/temp files *inside* `bin/`/`lib/` (next to the executables) therefore fails. The fix keeps the FS read-only and stacks a stock `overlayfs` writable upper **over** the decrypted antirevfs lower: `overlayfs(upper=writable ext4)` on top of `antirevfs(ro, decrypt-on-read)`. Decrypted `.so`/`.elf` reads fall through to the antirevfs lower; the app's runtime writes land in the overlay upper and never touch the `.enc/` ciphertext. `antirev-mount-rw [--passdata|--passthrough exts] [--state <dir>] <encdir> <mountpoint>` mounts both layers (default layers under `<dirname mp>/.antirev-rw/<basename mp>/{dec,upper,work}`; `--state` can point at tmpfs to wipe writes on reboot); `antirev-mount-rw --down <mountpoint>` tears them down in order (overlay then antirevfs, preserving the upper). **Copy-up caveat**: overlayfs copies a file up into the upper as *decrypted plaintext* on first modification — only triggered by *rewriting an existing encrypted file* (business code doesn't; new lock/log files never copy up). Covered by `kmod2/tests/test_antirevfs_overlay_rw.sh`.
- **Packer** (`kmod2/tools/antirev-fs-pack.py <config.yaml>`): the antirevfs-side analog of `encryptor/antirev-pack.py`. Where `antirev-pack.py` builds stub/daemon/shim artifacts, this tool produces the **ciphertext lower tree** antirevfs mounts over. It walks `install_dir`, encrypts **every ELF** (shared libs AND executables — detected by `\x7fELF` magic, not extension) into a mirrored `output_dir/` tree via `protect.py`'s `make_container(data, key, embed_key=True)` — the **embedded-key trailer** form (`MAGIC+iv+tag+ct+key+MAGIC`) so `read_folio` finds the key per file with no mount key — and writes a JSON manifest *outside* the tree. Config fields: `install_dir`, `output_dir`, `key` (hex keyfile relative to the config, created 0600 if absent), optional `blacklist` (basename globs like `libprotobuf.so*`, or `prefix/` path subtrees — left UNencrypted for third-party libs that coexist plaintext), optional `mirror_plaintext` (default **true**). **`mirror_plaintext` (default) produces a COMPLETE mixed-content tree**: ELFs are encrypted; every other regular file (`.py`/`.pyc`/`.sh`/`.txt`/`.json`/resources) **and** blacklisted (intentionally-plaintext third-party) ELFs are **mirrored verbatim (plaintext) into the tree** (via `copy_verbatim`), and symlinks re-created — so a real `lib/`/`bin/` appears in full under a `passdata` mount. Set `mirror_plaintext: false` for a minimal pure-secret tree (only encrypted ELFs + symlinks land in the tree; data files and blacklisted ELFs are omitted and will NOT appear under the mount — point it at pure-ELF subtrees). The manifest gains a `plaintext` list (mirrored files) alongside `encrypted`/`symlinks`. **Symlinks are mirrored verbatim** so SONAME version chains (`libfoo.so → .so.1 → .so.1.2.3`) keep resolving through the mount. Because the mount is read-only, runtime-written files (python `.txt`, `__pycache__`) must be redirected to a writable path outside the mount. - **Threat model + the decrypt-on-read leak (data-in-use boundary)**: antirevfs protects **data at rest**, not **data in use** — the mount point is a real path that hands plaintext to *any* reader (when the gate allows), so `cp /proj/lib/foo.so /usb/` from inside the app's context exfiltrates a clean plaintext ELF; the **mount view** is the leak. **NOTE (embedded-key scheme)**: the `.enc/` lower tree is **no longer safe to copy** — each file now carries its AES key in its trailer, so a raw copy of `.enc/` is decryptable. Two consequences: (1) the lower tree must stay namespace-isolated (it's now key-bearing, not inert ciphertext); (2) through the mount, an *unauthorized* reader gets the trailer **stripped** (keyless container) so the GUI/USB-copy path still yields useless bytes. This is the #1 vector to reason about, judged against a **two-tier adversary**:
    - **At-box adversary = the client** — physically owns HW+SW but is a *non-technical operator* (GUI buttons, drag-and-drop, copy-to-USB; no concept of root, mount namespaces, decryption, or memory forensics). Attack: "copy the software folder and hand it to someone."
    - **Capable adversary = the competitor** — expert reverse-engineers, but **decoupled from the live appliance**; they only ever receive the bits the rookie copied, never root on a running box (no `nsenter`/`gcore`/page-cache dump).
    - **Consequence**: the whole problem reduces to *"what a non-technical user can copy via GUI/USB must be ciphertext."* Sophisticated-root attacks are genuinely out of scope — the at-box person can't do them and the person who can isn't at the box. (This corrects an earlier framing that treated the at-box adversary as root-capable.)
    - **Primary mitigation — namespace-isolate the plaintext mount**: launch the business app via a wrapper that `unshare -m`s (or a systemd unit with `PrivateMounts=yes`) and mounts antirevfs *inside* that namespace, so a normal GUI/file-manager session sees only the `.enc/` ciphertext tree — there is no plaintext path for the rookie to navigate to. Under this threat model isolation is **sufficient, not theater**: the rookie can't bypass it (doesn't know namespaces exist) and the competitor never reaches the box to `nsenter`. **Caveat under the embedded-key scheme**: a whole-disk/USB copy captures `.enc/` *with the embedded keys inside it*, so the namespace isolation (keeping the rookie off the `.enc/` lower path) and the mount's trailer-strip are now the load-bearing protections — there is no separate key blob to withhold. Wrapping the per-file key (obfuscation / TPM-sealing the trailer) is the way to restore "exfiltrated ciphertext is also undecryptable" ([[project_key_obfuscation]], [[project_hardware_key_token]]).
    - **Backstop — TPM per-unit sealed key** (see deployment/key-mgmt notes): makes any exfiltrated ciphertext doubly useless — the competitor can't decrypt it (key never left the box) and can't even run it on other hardware (key won't unseal against a different TPM/PCRs).
    - **Boundary case — coached rookie**: a rookie talked through `nsenter`/`cp` over the phone escalates toward competitor-at-box. Optional belt-and-suspenders: **PROT_EXEC-gated decryption in `read_folio`** (serve plaintext only to executable faults; plain `read()`/`cp` → ciphertext or `-EIO`) defeats even a coached `cp`, leaving only a hard-to-coach memory dump. Not required for the solo-rookie case; must be done carefully so `ld.so`'s non-exec header/`.rodata` reads still load.
    - **Fundamental limit**: the CPU executes plaintext, so plaintext is in RAM, so ring-0/root can always read it — no kernel-FS trick (nor the memfd design) beats that. Only hardware memory encryption (SEV-SNP / TDX / enclaves) changes the theorem; out of scope given the adversary model above.
- **Decrypt-authorization gate (`module/gate.c`)**: per-process gating so only an *authorized* process can open an encrypted file and reach plaintext via the shared page cache; `cp`/backups/file-managers get `-EACCES` and can only ever read the lower `.enc/` ciphertext. Policy lives behind two seams in `antirevfs_file_open()`, applied *only to encrypted files* (`ii->encrypted`), enforcing with `-EACCES`. Gating at **open** (before any read/mmap/splice) is what lets the business app load natively through the shared plaintext cache while everyone else is denied — it does not duplicate physical pages (authorized openers share one cache; unauthorized never open).
    - **Exec-load vs data-read use different identities (critical):** at `execve`, the kernel opens the program *before* `current->mm->exe_file` becomes that program — it's still the caller (the shell) — so gating an exec-load on the caller's exe would deny **every** encrypted executable (catch-22: the binary can't authorize its own launch). So `antirevfs_file_open()` splits on exec-intent (`arev_is_exec_open()` — `FMODE_EXEC` in `f_mode` on 4.12, `__FMODE_EXEC` in `f_flags` on mainline 6.8 where `FMODE_EXEC` is clear at `->open`; `current->in_execve` is NOT usable here because the kernel opens the binary in `alloc_bprm()` before `bprm_execve()` sets it): an **exec-load** is gated by `antirevfs_file_authorized(file)` on the **program's OWN path** (running a program is not a plaintext-file exfiltration vector — bytes land only in the new process's executable mapping); **every other open** (lib loads, `cp`, `source`) is gated by `antirevfs_task_authorized()` on the **calling process's exe** (`current->mm->exe_file`), which is what keeps `cp` on ciphertext. So a listed binary runs *and* its lib loads pass (running exe == listed), while `cp` of that same binary is denied.
    - Data-read lifecycle is free: `current->mm->exe_file` is updated by the kernel at `execve`, so **`fork()` inherits authorization and `execve()` of an unlisted helper (e.g. an authorized app shelling out to `/bin/cp`) drops it** with no task bookkeeping.
    - **Step 1 (implemented)** — `authz_exe_allowed()` resolves `current`'s exe path (`arev_get_mm_exe_file` + `d_path`) and matches it against a newline-separated allow-list file (module params: `gate_enforce` bool default 0 = allow-all so existing tests are unaffected; `authz_path` default `/etc/authorized_apps.txt`). An entry with `/` matches the full path, without `/` matches the basename; `#` comments and blanks ignored; re-read per-open so the list can be edited live. This is a **correctness demonstrator, not a security boundary** — anyone who can write the allow-list or place a binary at an allowed path passes. The allow-list is opened with the caller's creds, so it must be readable by the business processes (e.g. 0644). Covered by `kmod2/tests/test_gate.sh` (authorized read allowed; `cp`/`cat` denied; byte-identical-but-unlisted loader denied → gates on *identity* not action; authorized parent's `cp` child denied → execve lifecycle; `gate_enforce=0` control proves the gate is the enforcer; lower file still ciphertext).
    - **Deny posture — `gate_passthrough_cipher` (module param, bool, default 0)** — controls what an *unauthorized data read* gets. Default (0): hard `-EACCES`. When 1: serve the lower `.enc/` ciphertext **with the key trailer stripped** — `antirevfs_file_open()` opens the lower file `O_RDONLY` and stores a per-open `{lower, limit}` (`struct antirevfs_passthrough`) in `file->private_data` where `limit = lower_size − TRAILER(40)`; the data ops serve from the lower file **capped at `limit`** so the embedded key is never exposed: `read_iter` (bounce `arev_kernel_read`→`copy_to_iter`, clamped), `splice_read` (clamps `len`, delegates to the lower `f_op->splice_read`, covering `sendfile`/`copy_file_range`), `llseek` (`generic_file_llseek_size` against `limit`). **`mmap` is refused (`-ENODEV`)** — a file-backed mapping of the lower file would surface the trailer in its final page; readers fall back to `read()`. All of this **bypasses this inode's `i_mapping`** (a concurrent authorized reader may have cached plaintext there). `getattr` reports the *trailer-stripped* length (`lower_size − 40`) to unauthorized callers so size-honoring copiers grab the whole keyless container. Net effect: `cp`/`vim`/`objdump` "succeed" but get a valid-but-useless **keyless** container (`objdump` → "file format not recognized") — **no plaintext AND no key escapes**; only the posture/stealth differs from `-EACCES`. Scope: **data reads only** — exec-load of an unlisted program stays `-EACCES` regardless. When `private_data` is NULL (authorized opener, or passthrough off) the ops fall through to the plain `generic_file_*` decrypt path. Covered by `kmod2/tests/test_gate_passthrough.sh` (authorized read still decrypts; `cp` yields exactly `enc−40` bytes with the embedded key absent; `cat` sees `ANTREV01` magic; `objdump` refuses it; flipping the param to 0 restores `-EACCES`; lower file still ciphertext). The reference deployment (`antirev-remount-proj.sh`) sets `gate_passthrough_cipher=1`.
    - **Step 2a (implemented) — signed allow-list (`gate_require_sig`)**: makes the allow-list tamper-proof so an unprivileged **client cannot edit it**. The plaintext `authz_path` is only trusted if a **detached PKCS#7 signature** at `authz_sig_path` (default `<authz_path>.p7s`, DER) verifies against the **vendor public key embedded in the module** (`module/gate_authz_pubkey.h`, an X.509 DER cert). `authz_path_listed()` reads the list bytes + length and, when `gate_require_sig=1`, calls `authz_list_signature_ok()` → `verify_pkcs7_signature(list, len, sig, sig_len, authz_keyring, ...)` **before** matching (fails safe: missing/edited/badly-signed list, no embedded key, or a kernel lacking `CONFIG_ASYMMETRIC_KEY_TYPE`/`CONFIG_PKCS7_MESSAGE_PARSER` ⇒ list rejected ⇒ deny). `antirevfs_authz_init()` (called from `super.c` module-init) builds a trusted keyring `.antirev_authz` holding only the embedded cert; `antirevfs_authz_exit()` releases it. **Default `gate_require_sig=0`** keeps the legacy plaintext list (existing setups/tests unaffected); the entry-matching logic (`/`→full path, no-`/`→basename) is identical either way — only the *trust* of the list bytes changes. The client gets the module (public key) + a signed list and can neither edit the list (edit invalidates the signature) nor forge a new one (no vendor private key). **Toolchain** (`kmod2/tools/`, standard openssl, round-trip verified): `authz-keygen.sh` (vendor RSA keypair + self-signed X.509, private key never ships), `authz-embed-pubkey.sh <cert.der>` (generates `gate_authz_pubkey.h` — placeholder cert of length 0 is checked in so the module builds; regenerate + rebuild to enable), `authz-sign.sh <priv> <cert> <list>` (`openssl cms -sign -binary -noattr -md sha256 -outform DER` → detached `.p7s`, self-checked with `openssl cms -verify`). Covered by `kmod2/tests/test_gate_rsa.sh` (builds a throwaway module embedding a test key — source tree untouched — then: signed list authorizes; **editing the list without re-signing denies**; restoring re-authorizes; removing the `.p7s` denies; `gate_require_sig=0` honors the plaintext list = the sig gate is the enforcer). NOT yet built/tested on a real kernel (no toolchain in this env); the `verify_pkcs7_signature` call + `keyring_alloc` signature are the kernel-version-sensitive spots to confirm on SLES 4.12 / mainline.
    - **Step 2b (planned) — per-exe signature + TPM**: for the strongest posture, verify `current->mm->exe_file`'s own detached signature (xattr/trailer) rather than a list, with the key in a **locked kernel keyring anchored in TPM measured boot** (a tampered kernel won't unseal the AES key). Removes the allow-list entirely; the call site, `-EACCES` enforcement, encrypted-only scoping, and fork/execve lifecycle stay unchanged. Optionally cache the verdict via an exec-time LSM `bprm_check_security` hook + task flag (perf only).
- **Not yet done**: module signing for Secure Boot, key rotation, DKMS `.deb`/`.rpm` packaging, gate step 2b (per-exe signature + TPM; step 2a signed-allow-list is implemented behind `gate_require_sig`, pending real-kernel build/test), **Docker/container-namespace validation of the qemu-user path (qemu-user itself is now verified — see section below)**.

### kmod2: qemu-user (ARM64-on-x86 "sim mode") — qemu-user VERIFIED; Docker still untested

Deployment has an **RTOS slave** whose software is **ARM64**, run on an **x86-64 host** via **`qemu-user-static`** (binfmt_misc), sometimes inside **Docker**. The **qemu-user path is now runtime-verified** on the x86-64 dev box (6.8.0-124) by `kmod2/tests/test_antirevfs_qemu.sh` — 10/10, including the binfmt exec-load gate split. **Docker/container-namespace behaviour is still untested** (no usable daemon in CI). Findings:

- **Decryption is arch-agnostic — VERIFIED.** antirevfs decrypts `ANTREV01` containers in `read_folio` without parsing ELF arch; the x86 `.ko` serves an AARCH64 ELF byte-for-byte (test 1 confirms `e_machine=0xb7`), and an ARM64 program run under `qemu-aarch64-static` dlopen+calls an *encrypted* ARM64 `.so` read through the mount (test 2 → 42). `qemu` `open()`/`mmap()`s the ARM64 binary + `ld.so` + libs through the host kernel → reads hit antirevfs → plaintext ARM64 bytes emulated. (A *better* fit than the LD_PRELOAD/shim arch — transparent at the FS layer, no preload injection into the emulator.) Dynamic ARM64 binaries need `QEMU_LD_PREFIX` pointed at a guest aarch64 sysroot (`/usr/aarch64-linux-gnu` on the dev box) holding `ld-linux-aarch64.so.1` + libc.
- **Gate keys on the emulator's identity — VERIFIED.** Under qemu-user the process's `current->mm->exe_file` is **`qemu-aarch64-static`**, not the ARM64 binary (qemu emulates `/proc/self/exe` to point at the guest program, but the *kernel's* exe_file is the interpreter). So with `gate_enforce=1`, ARM64 lib/data reads (qemu's non-exec `open()`s) are gated by `antirevfs_task_authorized()` against **qemu's** path ⇒ **whitelist `qemu-aarch64-static`** (basename, like `python3`); empty list → `-EACCES`, dlopen fails (test 3). The distro binfmt entry's interpreter (`/usr/libexec/qemu-binfmt/aarch64-binfmt-P`) is a **symlink to `qemu-aarch64-static`** registered with flag `F` (fix-binary), so the resolved exe_file basename is `qemu-aarch64-static`. The ARM64 *exe*'s exec-load is opened `FMODE_EXEC` by the host kernel *before* the binfmt redirect, so `arev_is_exec_open()` gates it on its own path ⇒ a transparently-run encrypted ARM64 exe on the mount needs BOTH its own basename AND `qemu-aarch64-static` whitelisted; dropping the exe denies the exec-load (test 4, `EACCES`/126). Caveat: whitelisting the emulator lets any ARM64 binary under that qemu decrypt (broad, but matches the `python3` grant).
- **Docker/namespace gaps (STILL the risky part — untested).** (a) The antirevfs mount must be visible in the container's mount ns (bind/volume) ⇒ **decrypted plaintext is exposed inside the container** — revisit namespace-isolation mitigation. (b) The gate's `authz_path` (`filp_open("/etc/authorized_apps.txt")`, caller's creds/root/mnt-ns) resolves to the **container's** `/etc`, not the host's — the allow-list must live inside the container. (c) `d_path(exe_file)` is **container-relative** ⇒ whitelist by **basename** (the test already uses basenames). (d) `gate_enforce`/`authz_path` are host-global module params but file/path resolution is per-namespace — that mix is unexercised.
- **Docker bring-up (`kmod2/tools/antirev-mount-inplace.sh --mode sim`).** Field setup where the ARM64 slave software is **baked into the image** at `/root/proj/{bin,lib}` as ciphertext (no `-v` volume) and the container runs `--privileged ... slave_img /usr/sbin/sshd -D`. Because there's no host-side volume to mount over, and the business `docker run` / `/register -p yes` binfmt step / image must stay untouched, `sim` mode drives the mount **into the running container** via `docker exec` — legal because the container is `--privileged` (`CAP_SYS_ADMIN`) and the `antirevfs` fstype is registered kernel-globally once the `.ko` is `insmod`'d on the **host**. **A mode expands to a LIST of mount targets (host is always one):** `antirev-mount-inplace.sh --mode real|sim` (default `real`). **`real` = HOST only** (the machine's own `/root/SW`; the real ARM64 slave is a separate box, handled later). **`sim` = HOST + CONTAINER** — it mounts the host's `/root/SW` AND, via `docker exec`, the slave software inside the qemu-user Docker container, in one invocation (the container half is skipped with a note if it isn't running). **Always run ON THE HOST** — `sim` reaches into the container for you; you never run the script inside the container. The per-target executor is a `TARGET`-driven `target_bash`/`run_in_target` (host→local, container→`docker exec`); the same in-place layover (lower == mountpoint) over `bin/`/`lib/`, tmpfs write layers (no overlayfs copy-up plaintext hazard), and gate allow-list run for each target. The container name is a constant (`CONTAINER=`/`AREV_CONTAINER=`). **Overlay-lower staging (SLES 4.12 + Docker — critical).** FIELD FACT (verified 2026-08): on SLES 12 SP5 `4.12.14-120` antirevfs **cannot positioned-read an `overlayfs` lower** (Docker's image layer / overlay2). The offset-0 magic read sneaks through — so plaintext files and `readdir`/`cd`/`ls` metadata work — but the offset-`(size−8)` trailer read and the decrypt reads return `-EIO`, so **every encrypted file fails with `EIO`** through a mount whose lower is the container image. Symptom: `ls /root/SW/bin` → `EIO` on every encrypted binary while the plaintext `libPreload.so` lists fine; native decrypt over an ext4/tmpfs lower works. Fix baked into the tool: `STAGE_LOWER` (`auto`|`always`|`never`, default `auto`) — when the mountpoint's fs is overlayfs, `cp -a` the **ciphertext** (still encrypted, safe) onto a real fs (`STAGE_DIR`, default `/dev/shm/arev` tmpfs, sized by the container `--shm-size`) and mount antirevfs from THERE instead of in-place; costs RAM = ciphertext size. On a real-fs lower (native appliance) `auto` stays in-place. **Only the executor differs** — a `target_bash`/`run_in_target` abstraction — so flipping `--mode` changes nothing above the mount layer. **Host-side logic is byte-identical across modes:** module load + gate params + mount-command construction always run the same, locally, on the kernel that backs the mounts (in `sim` the `--privileged` container *shares the host kernel*, so "load on the host" is that same kernel; `real` mounts only the host). The `TARGET` per-iteration redirects `do_up`/`do_down`/`write_allowlist`/`do_status` from local execution (host) to `docker exec <container>` (container); `sim` loops over both. Module (re)load is governed by `RELOAD_MODULE` alone (not the mode; **defaults to 0** so a shipped machine's boot-loaded module isn't churned on every container restart — set `AREV_RELOAD_MODULE=1` for `.ko` dev iteration); `up` tears mounts down before reloading so live mounts don't pin it. The sim container name is a **constant** in the config (`CONTAINER=`, or `AREV_CONTAINER=`), not a CLI arg. Actions `up|down|status|watch`: **`watch`** is a long-lived **daemon** for the **ship lifecycle** (OS+antirevfs pre-installed, machine shipped *without* the container; client installs+boots the sim stack at an unknown later time, across reboots). Critical separation: **the install script must not block** — it drops the unit, `systemctl enable --now`s it, and returns; **only the daemon waits**. `watch` is a **race-free, docker-optional poll** (edge-triggered on the container's down→up transition, `AREV_WATCH_INTERVAL` default 5s) — deliberately *not* `docker events` (which has a missed-start-event race and dies if docker isn't installed yet). It tolerates docker / the daemon / the container being absent indefinitely and mounts the instant the container appears, re-mounting on every restart; also covers the **dev** case (mounts within one poll if already up). `up` is the immediate one-shot (fails fast if the sim container is down). Real-mode ship is a `oneshot` `up` at boot ordered `Before=` the business app. Ship templates: `kmod2/tools/antirev-sim.service` (sim watch daemon, `Restart=always`, `After=/Wants=docker.service`) and `antirev-real.service` (real oneshot). So both lifecycles — container-already-running and container-boots-later — are handled by one tool without ever blocking the installer. The **container-local** `/etc/authorized_apps.txt` is what the gate reads (it resolves `authz_path` in the container's mount-ns; match by **basename**). Plaintext exists **only inside the container's mount namespace** — the intended namespace-isolation posture. Bring-up order it encodes: `GATE_ENFORCE=0` to prove decrypt+qemu first, discover write paths via EROFS, then `GATE_ENFORCE=1` with basenames (`qemu-aarch64-static` + every slave exe). Symptom it fixes: an encrypted binary in the container giving **"Exec format error" (`ENOEXEC`)** because the kernel was reading raw `ANTREV01` bytes (no mount decrypting them) — distinct from a gate `-EACCES` ("Permission denied"). **Still untested in CI** (needs a usable docker daemon); the in-place overmount inside a container mount-ns is the specific unverified path.
- **Remaining action items:** (1) Docker run of `test_antirevfs_qemu.sh` (mount in container ns, in-container allow-list, basename whitelist) once a usable daemon is available; (2) document/measure the in-container plaintext-exposure tradeoff against the namespace-isolation mitigation. Bring-up order that worked: `gate_enforce=0` to validate pure decrypt/emulation first, then enable the gate and whitelist `qemu-aarch64-static` + the ARM64 program basenames.

### kmod2 deployment gotchas (field-discovered)

Bringing a real business stack up on antirevfs surfaced interactions that aren't obvious from the module/tool code. Reference layout where these were found: ciphertext lower tree `/root/proj_protect/{bin,lib}`, mounted at `/root/proj/{bin,lib}` as **writable overlay views** (`antirev-mount-rw`, overlayfs upper over the antirevfs lower) with `passdata` + `gate_enforce=1` + `/etc/authorized_apps.txt`; the stack sets a **global `LD_PRELOAD`** to a custom `libPreload.so`. **Both `bin/` and `lib/` are writable** — the business stack writes runtime files (pid/lock/log) next to binaries in *either* tree, so each is a writable overlay view; decrypted `.so`/`.elf` reads fall through to the antirevfs lower while writes land in that view's overlay upper and never touch the ciphertext. Helper `kmod2/tools/antirev-remount-proj.sh` automates the umount→rmmod→insmod→key-unlock→mount cycle (re-execs under sudo + one `keyctl session`, mounts both trees rw via `antirev-mount-rw` — `LIB_WRITABLE=1` default; set 0 for a read-only `lib/` — collapses leftover overlays on both mounts, sweeps proj mounts deepest-first, reload-checks via `/sys/module/antirevfs`).

- **A globally-preloaded lib (and its whole `DT_NEEDED` closure) must be plaintext.** `LD_PRELOAD` is inherited by *every* descendant (shells, `env`, helpers, processManager children), and the gate authorizes an encrypted-file open by the **consumer process's** identity (`antirevfs_task_authorized` → `current->mm->exe_file`). So an *encrypted* preload lib would require whitelisting every process that ever inherits it — impractical. Keep `libPreload.so` **and its transitive deps** (e.g. third-party `libsecurec.so` in `lib/link/3rd`) plaintext; under `passdata` any non-`ANTREV01` file is served verbatim and ungated. The durable fix is to **blacklist all third-party subtrees (`link/3rd`) in `antirev-fs-pack.py`** so they never get encrypted — otherwise you chase the dependency closure one lib at a time.
- **Cached inode classification on remount.** antirevfs decides encrypted-vs-plaintext **once per inode at first lookup** (`iget5` keyed on the lower dentry) and caches it. After swapping a lower file cipher↔plaintext you **must remount** that mount, or the stale "encrypted" classification persists and reads fail (`-EACCES` through the mount even though the lower bytes are now a plain ELF).
- **ld.so failures: read the errno, not the generic text.** `ld.so` prints "cannot open shared object file" for many causes and masks per-candidate `EACCES` as a final "No such file or directory". Decode by running the open directly (`head -c 16 <lib> | xxd`) / checking the real errno: `Permission denied`=`EACCES`=**gate** (consumer not whitelisted, or file still encrypted); `Required key not available`=`ENOKEY`=**key not in this mount's session keyring** (unlock + mount must share one `keyctl session`); `No such file or directory`=`ENOENT`=not on the search path **or** found-but-invalid-ELF (served ciphertext / wrong arch); `Error 30` / `Read-only file system`=`EROFS`=app writing inside the RO mount.
- **Writable view is mandatory for apps that write next to their binaries — for BOTH `bin/` and `lib/`.** Real example: the GUI (`NVUI`) writes `QtApplication.pid` into `bin/` → `EROFS` on a bare antirevfs mount. The business stack also writes runtime files into `lib/`, so the reference deployment mounts **both** trees with **`antirev-mount-rw`** (overlayfs upper over the antirevfs lower); decrypted reads fall through, runtime writes land in each view's overlay upper. Two concurrent writable views coexist on one loaded module (independent `dec`/`upper`/`work` state dirs under each mount's `.antirev-rw/`). Only set a tree read-only (`antirev-mount` / `LIB_WRITABLE=0`) if you are sure nothing writes into it.
- **Python loaders are gated by the interpreter's identity.** A python subprocess `import`ing an encrypted `.so` is denied unless the **interpreter** (`python3`/`python`/`python3.9` — match what the subprocess actually execs, by basename) is in the allow-list, or the `.so` is plaintext. Whitelisting a generic interpreter broadens the gate (any python can decrypt) — acceptable under the rookie/competitor threat model, but prefer plaintext for third-party extension modules.
- **`boost::process` child launches.** `boost::this_process::environment()` captures the **launcher's** env, so processManager itself must already carry `LD_LIBRARY_PATH` for dep dirs (`link/3rd`) — an empty `boost::process::environment` wipes it. A robust alternative is an `$ORIGIN` RUNPATH on `libPreload.so` (`patchelf --set-rpath '$ORIGIN:$ORIGIN/../3rd'`) so its deps resolve without any consumer env. Relative exe paths resolve to the canonical `d_path()` the gate matches — and the install tree uses `link/` **symlink** dirs, so the canonical path differs from a symlink-containing abs path; use **basename** entries in `/etc/authorized_apps.txt` to avoid the mismatch.
- **Allow-list by BASENAME is mandatory under `antirev-mount-rw` (not just preferred).** With the overlay-rw writable views, the gate sees the *same program* at **two different absolute paths** depending on the check: an **exec-load** opens through the overlay as a backing file whose `f_path` is the antirevfs lower (`.../​.antirev-rw/bin/dec/<module>/<exe>`), so `antirevfs_file_authorized()`'s `d_path()` reports the `dec/` path; a **data read** the program then performs is gated on `current->mm->exe_file`, which is the overlay-top file (`/root/proj/bin/<module>/<exe>`, what `/proc/pid/exe` shows). Different prefixes, **same basename** — so a full-path entry can never match both halves of one binary's lifecycle. Put bare basenames in the allow-list (process manager, every executable, `qemu-aarch64-static` for the sim path). The exec-load gate fires correctly through the overlay because `__FMODE_EXEC` rides in `f_flags` and overlayfs's `OVL_OPEN_FLAGS | file->f_flags` reopen does not strip it (verified end-to-end by `test_proj_setup.sh`). Reference pack config: `kmod2/examples/proj-pack.yaml` (blacklists `lib/link/3rd/` + `libPreload.so`).
- **Module reload requires a quiet stack.** mmap'd `.so` files pin the antirevfs superblock (hence the module) even after the mount is gone — and a `umount -l` leaves the superblock alive until the last mapping closes. Stop the business stack before `rmmod`. Leftover `antirev-mount-rw` `dec` mounts (e.g. `/root/proj/.antirev-rw/lib/dec`) also pin the module; collapse the overlay (`antirev-mount-rw --down`) first. Check `/sys/module/antirevfs/refcnt` (1 per live antirevfs mount).
