# antirev

Binary protection system that encrypts executables and shared libraries, then runs them from memory (memfd) to prevent reverse engineering. Key components:

- **stub**: C launcher that decrypts bundled binaries into memfds and executes via `fexecve`
- **antirev_shim**: the single LD_PRELOAD shim — one `.so` per arch (`antirev_shim_x86_64.so`, `antirev_shim_aarch64.so`). Bundles every interceptor into one DSO so the stub only writes one memfd and adds one entry to `LD_PRELOAD`. Sources:
    - `stub/exe_shim.c` — `readlink` / `realpath` / `getauxval` identity hide
    - `stub/dlopen_shim.c` — `dlopen()` redirect to `/proc/self/fd/N` (eager via `__r_FM`, lazy via daemon `OP_GET_CLOSURE`)
    - `stub/aarch64_extend_shim.c` — aarch64-only, compiled as an empty TU on x86: `ANTI_LoadProcess(struct ANTI_ProcessInfo *)` hijack + `popen`/`pclose` workaround (glibc's vfork-based popen corrupts memfd-heavy parent processes on this arch). CMake conditionally adds the file to `antirev_shim` sources only on aarch64; x86 builds don't pull in any of its code.
    - `stub/daemon_client.c` — shared daemon-protocol client owning the socket fd (`__r_LS`), the eager fd map (`__r_FM`), and the encrypted-name set (`__r_EL`). Both `dlopen_shim` and `aarch64_extend_shim` talk to the daemon through `daemon_client_send` / `daemon_client_recv` and check encryption / eager-lookup state through accessors instead of carrying private copies. Init is idempotent — each shim's constructor calls `daemon_client_init()` and only the first call reads env vars.

    Each source file keeps its own concern (identity, dlopen, ARM-only, daemon transport) with disjoint symbol exports and independent file-scope state where it makes sense to stay isolated (per-shim caches, mutexes, log files).
- **hot-patch shim** (`stub/patch_shim.c` → `lrxd_<arch>.so`): a separate, keyless `LD_PRELOAD` shim for **hot-patch / live-patch tooling**. Loaded into an *unprotected* injector process; intercepts `open`/`open64`/`openat`/`openat64` **and the stdio `fopen`/`fopen64`** of encrypted `.pat` files and returns the daemon-decrypted memfd so the injector reads plaintext transparently. Fully self-contained: no key, no crypto, no `daemon_client.c` — a pure socket client that finds the daemon via the discovery file (see "Hot-patch support" below). Deployed artifact is named `lrxd_<arch>.so` to blend in next to the `lrxd` daemon binary (CMake target stays `antirev_patch` — internal id only). Deliberately NOT part of `antirev_shim`; its `open`/`openat` interceptors are independent of `aarch64_extend_shim`'s `.elf` `openat` redirect and are only ever loaded into the injector, never a protected process.
- **encryptor** (`protect.py`, `antirev-pack.py`): Python tools that encrypt and bundle binaries with AES-256-GCM
- **daemon mode** (`lrxd`): a lightweight lib-server process that scans `$HOME/SA` (the suite's install tree; falls back to its own directory when `$HOME/SA` is absent) for encrypted `.so` / `.elf` files, decrypts them into memfds, and serves the fds to client processes via SCM_RIGHTS.  Pinning the scan root to `$HOME/SA` lets the daemon live in a subdir (e.g. `$HOME/SA/bin`) while still serving libs from the whole tree (e.g. `$HOME/SA/lib`).  (Filename was `.antirev-libd` historically, then `.lrxd`; the leading dot was dropped because a hidden *executable* is itself a red flag, and dotfiles get skipped by glob/rsync copies — plain `lrxd` blends in with ordinary binaries and copies cleanly. Multi-arch deploys get `lrxd-x86_64` / `lrxd-aarch64`.)
- **antirev_client.py**: Python client that connects to the daemon, receives decrypted lib memfds via SCM_RIGHTS, and patches `import` + `ctypes.CDLL` to transparently load encrypted libs. Handles dependency ordering via `_ensure_loaded()` which recursively preloads transitive DT_NEEDED deps with `RTLD_GLOBAL`.
- **build.py**: compiles/obfuscates Python source files via Cython, Nuitka, or PyArmor

## Target environment

This project protects a business software suite consisting of:
- 100+ executables
- 550+ shared libraries
- 1000+ Python scripts (some of which dlopen encrypted .so files)

The business software also uses third-party libraries (e.g. `libdopra.so`, `libprotobuf.so`, open62541, Boost) which are NOT encrypted but coexist in the same processes.

## Architecture notes

- Protected binaries run from memfd via `fexecve`. `/proc/self/exe` points to `memfd:<random-hex> (deleted)`.
- **qemu-user exec + name visibility (`__r_FX`)**: under qemu-user (aarch64 container on an x86 host, binfmt_misc), the aarch64 stub launching an aarch64 target makes `needs_qemu_for_fd()` (a compile-time-arch compare) report "native", so `exec_target` takes the plain `fexecve` path. That path *succeeds* via binfmt_misc's auto-wrap (`qemu /proc/self/fd/N`), but binfmt drops the real `argv[0]` — the guest cmdline becomes `qemu-aarch64-static /dev/fd/N` with no program name, so anything that finds the process by name (`ps -o cmd | grep <name>`, `pgrep -f`) fails. That breaks business restart/keepalive scripts: the old instance can't be found, isn't killed, and keeps its listening socket → the next start hits `EADDRINUSE`. The `-0 <binname>` fix in `exec_target` only runs on the explicit-QEMU dispatch, reached on `fexecve` ENOSYS or when **`__r_FX`** is set. Set `__r_FX=1` in the deployment env (one global var, like `__r_NP`, no per-binary work) for the docker+qemu deployment to force the explicit dispatch so the guest keeps its real `argv[0]`. **Placement matters:** export it in the *top-level* startup script — a parent of *every* protected process. `export` inside a sub-script invoked as `sh sub.sh` only reaches that sub-script's own children (e.g. `lrxd`) and dies when it returns; the sibling business processes the parent launches afterward never inherit it (verify per-process with `grep __r_FX /proc/<pid>/environ`). There is no auto-probe: qemu-user is transparent (`uname`, `/proc/self/exe` report aarch64 — exactly why `needs_qemu_for_fd()` misfires) and `binfmt_misc` isn't readable from inside the app container (its registration is kernel-global so emulation works, but the `/proc/sys/fs/binfmt_misc` interface lives in the host mount namespace and isn't mounted in the container), so the env var is the deliberate signal. `binname` is taken from `argv[0]` (binfmt's `P` flag passes the true program path), not `readlink(/proc/self/exe)` which under qemu can resolve to the qemu translator binary. Unset → identical to old behaviour, a no-op on native hosts.

  Why 708e77a's `-0` didn't fix this on its own: it was reached only on `fexecve` ENOSYS, but in this container `fexecve` *succeeds* via glibc's `execve(/proc/self/fd/N)` fallback + binfmt auto-wrap, so ENOSYS never fires and the dispatch was skipped. binfmt-based detection replaces that unreliable trigger.
- **Per-process random memfd name**: every memfd created by the stub or daemon (`make_memfd` in `stub.c`) shares a single name lazily derived from `/dev/urandom` on first use — 6 random bytes encoded as 12 hex chars. The protected exe, every daemon-decrypted lib, and the embedded `antirev_shim` blob all get the same name within one process, so `ls -la /proc/<pid>/fd/` and `cat /proc/<pid>/maps` can't tell which fd holds which encrypted artifact. Different processes get different names, so an attacker can't grep `/proc` for a fixed project marker across hosts. The kernel-prepended `"memfd:"` prefix is unchanged, so the shims' owner-process probe (`strstr(exe_buf, "memfd:")`) keeps working. Fallback when `/dev/urandom` is unavailable: `"x<pid>"` — kept short and non-revealing. Note: this is defense against external observation only — anyone who can `cat /proc/<pid>/fd/N` reads the decrypted ELF regardless of its name and can recover SONAME / symbols from the bytes themselves. Verified by `test_memfd_name`.
- The exe_shim constructor may run after C++ global static initializers in DT_NEEDED libraries. On x86_64, `is_owner_process()` handles this via lazy detection — the first interceptor call re-probes `/proc/self/exe` for `memfd:` and sets `g_owner_pid` on its own. On aarch64 the lazy path is compiled out; ownership is decided only inside the constructor (matching master's field-tested ARM behavior).
- Child processes inherit `LD_PRELOAD` but the shims detect non-owner processes (by checking `/proc/self/exe` for memfd) and pass through to real libc functions.
- **Owner-side env scrub (aarch64 only)**: on ARM the constructor also strips `/proc/self/fd/*` out of `LD_PRELOAD`, `/tmp/antirev_*` out of `LD_LIBRARY_PATH`, and unsets `__r_FM` even inside the owner process. The shims are already mapped, so env entries are only load-bearing for children spawned via `popen`/`system`/`fork+exec`; on ARM the business stack closes random fds and those children fail to start if they inherit `/proc/self/fd/N` preloads. x86_64 deliberately skips this scrub — its test matrix includes a protected parent forking a plain child that dlopens an encrypted lib through the daemon (see `test_fork_same_lib`), which requires the child to inherit `__r_FM` + the shim `LD_PRELOAD`.
- The daemon mode splits libs into DT_NEEDED (resolved via symlink dir on `LD_LIBRARY_PATH`) and dlopen'd (lazy, fetched on demand). DT_NEEDED libs are NOT on `LD_PRELOAD` — glibc's normal BFS resolves them through the symlink dir, preserving the original symbol lookup order. `LD_PRELOAD` contains only `antirev_shim` (one entry, both arches).
- **Symlink dir lifecycle**: each protected exe creates `/tmp/antirev_<pid>_XXXXXX` via `mkdtemp` in Phase 4c (the `<pid>` tag encodes ownership). Cleanup is two-tiered:
    - **Normal exit** — `exe_shim`'s ctor captures `__r_SD` into a static buffer and registers `atexit(cleanup_symlink_dir)`. Because `exe_shim`'s ctor runs very early and atexit is LIFO, the cleanup fires very late, after most shutdown work that might still walk the dir. Guarded by `is_owner_process()` so forked-non-execve children don't try to delete the parent's dir.
    - **Crash** (`SIGKILL`/segfault/`_exit`) — the daemon's `sweep_dead_symlink_dirs` walks `/tmp` at daemon startup and during clean shutdown, parses the `<pid>` out of each `antirev_<pid>_<rand>` name, and `rm -rf`s any whose owner PID is dead (`kill(pid, 0) == ESRCH`). Legacy no-PID names (created by old code paths) are skipped — without a PID we can't decide ownership safely.
    - **Python parallel**: `antirev_client.py` mirrors both halves — `tempfile.mkdtemp(prefix="antirev_<pid>_")` so the daemon reaper recognizes its dirs, plus `atexit.register(_cleanup_link_dir)` for normal exit.
- `antirev-pack.py` computes per-exe transitive DT_NEEDED using topological sort (Kahn's algorithm) to embed the needed-libs section. The stub uses this to create symlinks for the correct set of libs.
- **DT_NEEDED fd cleanup**: after glibc's dynamic linker has mapped the DT_NEEDED libs, their backing memfds are pure bookkeeping — the mappings keep the memfds alive. The stub passes the fd list via `__r_CF=n,m,...` and `exe_shim`'s constructor closes each one, freeing fd-table slots so that later `socket()`/`open()` land at low fd numbers. Matters for any code that still uses `select()` (FD_SETSIZE=1024).
- **Lazy dlopen fetch (Mode C daemon path)**: the stub only eagerly fetches the exe's encrypted DT_NEEDED set (filtered through `all_enc_names` from `OP_LIST`). The Unix socket to the daemon is kept open across `fexecve` and passed to the child via `__r_LS=<fd>`. `dlopen_shim` inherits `__r_EL` (comma-separated) and `__r_SD`; on each `dlopen()` of an encrypted basename it sends `OP_GET_CLOSURE` to fetch the lib plus its transitive encrypted DT_NEEDED closure in one round trip, materializes symlinks in the shared dir, then calls `real_dlopen` (glibc resolves via `LD_LIBRARY_PATH`). Returned fds are cached for the process lifetime to pin `/proc/self/fd/N` paths — closing and reusing them would make glibc collapse different libs into one link-map entry. The daemon parses each lib's `.dynamic`/`DT_NEEDED` at startup via `build_deps_graph()` so `OP_GET_CLOSURE` is a graph lookup. New opcodes: `OP_LIST`/`OP_NAMES`, `OP_GET_CLOSURE` (replies reuse `OP_BATCH`/`OP_END`).
- **Hot-patch support (`lrxd_<arch>.so` + `OP_GET_PATCH`)**: lets a business live-patch tool upgrade a running process without antirev coupling. Flow: (1) the operator drops an *encrypted* `.patch` file (`protect.py encrypt-patch` output — `ANTREV01` + iv + tag + ct, basename preserved; encrypted under the **keysplit-derived real key**, identical to the libs — see "Keysplit parity" below) into the daemon's scan dir; (2) the injector is launched with `LD_PRELOAD=lrxd_<arch>.so`; (3) when the injector `open()`s the `.patch` path, the shim discovers the daemon and sends `OP_GET_PATCH(basename)`; (4) the daemon resolves the basename under its scan dir, **re-reads part1 from its own `/proc/self/exe` trailer and runs the same `derive_real_key` keysplit derivation it used at startup** (part1 + SHA256(lrxd) + version) for this one decrypt (re-derived per request, then `explicit_bzero`d — key residency stays minimal), decrypts into a **fresh memfd per request** (independent file offset per client), replies with `OP_LIB` + fd, and closes its own copy; (5) the shim returns that fd to the injector, which reads plaintext. Design rationale (see chat history / decoupling discussion): the *business injector stays antirev-blind* — it calls plain `open()`; all antirev knowledge lives in the antirev-owned shim + daemon. There is **no `reload()` API** — patches are decrypted lazily on first `open()`, so the business/orchestration side never calls an antirev API; the contract is just "drop an encrypted file in a directory." `.patch` files are **not** scanned at daemon startup (`collect_enc_paths` only queues `.so`/`.elf`), so they cost nothing until requested.
    - **Keysplit parity (patch == lib)**: a `.patch` is encrypted/decrypted with the **keysplit-derived real key** (`SHA256(part1 ‖ SHA256(lrxd) ‖ version)`), NOT the bare trailer part1 — identical protection to the encrypted libs. So `protect.py encrypt-patch` requires `--lrxd` and `--version` (byte-identical to the target's `$HOME/SA/bin/sa/lrxd` + `$HOME/SA/version`), and the daemon's `handle_get_patch` re-derives via `derive_real_key` per request (`reload_part1_from_trailer` → `derive_real_key`). This closes an earlier gap where patches used part1 alone: part1 is *plaintext in every protected binary's trailer*, so a trailer dump would have decrypted every patch while the libs stayed bound to lrxd integrity + version. keysplit is **per-arch** (part2 = SHA256 of that arch's lrxd), so encrypt a patch with the lrxd of the arch it targets. Verified by a round-trip: the patch decrypts only under the derived real key; the bare part1 fails with InvalidTag.
    - **Deployment scope (native x86_64 + aarch64; not docker+qemu)**: this feature applies to **native deployments on both `x86_64` and real `aarch64` hardware**; the **docker+qemu environment (x86 host emulating aarch64 via binfmt_misc) does not use it**. The constraint is **not** build-enforced — the shim is built on both arches, and CMake's arch detection genuinely *can't* tell real-aarch64 from qemu-aarch64 anyway (qemu-user is transparent: `uname` / `CMAKE_HOST_SYSTEM_PROCESSOR` both report `aarch64`, the same reason `needs_qemu_for_fd()` misfires). Scope is enforced **operationally**: hot-patch is a *manual* action (the operator chooses to drop a `.patch` file and to `LD_PRELOAD=lrxd_<arch>.so` into the injector), so simply never preloading it in the qemu deployment keeps that environment uninvolved. No qemu start-script ever references it.
    - **Discovery file**: a keyless injector can't re-derive the key-hashed abstract socket name, so the daemon publishes its (non-secret) abstract socket name to `<scan_dir>/.antirev-libd.sock` at startup (before the daemonising fork; unlinked on clean shutdown). The shim locates it in **two steps**: (1) **fixed keysplit deployment path first** — `$HOME/SA/bin/sa/.antirev-libd.sock` (`find_discovery_fixed`), since keysplit hardcodes the daemon at `$HOME/SA/bin/sa/lrxd` so its discovery file is always there regardless of where the `.pat` lives; this is the zero-config path for a real deployment (a `.pat` opened from anywhere — e.g. an integrated `PatchServer` inside a protected business process reading a `.pat` from `$HOME/SA/lib/`). (2) **fall back to walking up** from the `.pat` path's directory (`find_discovery`) for the standalone-injector layout where the `.pat` sits inside the daemon's scan tree. Without step (1) the walk-up misses the daemon dir entirely when the `.pat` is on a sibling branch (`…/lib/foo.pat` never reaches `…/bin/sa/`). The filename is a plaintext literal in both `stub.c` and `patch_shim.c` — it sits next to the `lrxd` binary, which is already visible on disk, so it leaks nothing new (could be folded into `gen_obf.py` later if the shim takes on `obf.h`).
    - **Intercepted opens + `.pat` suffix**: the shim redirects the path-taking `open`/`open64`/`openat`/`openat64` **and the stdio `fopen`/`fopen64`** (read-only modes only). The stdio pair is **mandatory, not redundant**: glibc's `fopen`/`fopen64` open the underlying file through a *private internal open that does not go through the PLT*, so the `open`/`open64` interposers never see it — a loader that does `fopen64("foo.pat","rb")` would bypass the redirect unless `fopen64` itself is hooked. On a stdio hit the shim fetches the memfd and wraps it with the **real `fdopen`** so the caller gets a `FILE*` over plaintext (`fdopen` of an already-open fd takes no path, so it needs no hook). The matched suffix is **`.pat`** (the business patch artifact, an `.o`-style file) — decide hooks by what the loader actually calls (`nm` the loader: a `U <fn>` means it calls that libc fn, so that's the one to interpose).
    - **`.pat` lookup root + traversal guard**: `OP_GET_PATCH` resolves the basename under **`$HOME/SA`** (the whole install tree — the SAME root as the lib scan, falling back to the daemon's own dir when `$HOME/SA` is absent), NOT just the daemon's directory — so a `.pat` in `$HOME/SA/lib/` is found even though the daemon lives in `$HOME/SA/bin/sa/`. **Two distinct paths**: the *discovery file* is published in the daemon's own dir (`exe_dir`, where the shim's fixed-path lookup expects it), while the *`.pat` search root* spans `$HOME/SA` (`patch_root` in `run_daemon_forever`) — conflating them made the daemon reply `ST_NOT_FOUND` for a `.pat` outside its own dir. Names containing `/` are rejected, so only basenames under that root are served, never client-supplied paths.
    - **Conflict to watch**: an external `ptrace`/`process_vm_writev` injector is fine today (antirev has **no** ptrace interception), but is mutually exclusive with the future Layer-4 anti-debug measures (`PTRACE_TRACEME`, `PR_SET_DUMPABLE=0`, `TracerPid` polling). If Layer 4 lands, either whitelist the injector or move the patch-apply in-process (shim-driven). Function-level live patch of a no-`dlopen` exe is feasible because the apply machinery can live in the shim, not the app; cleanest with `-fpatchable-function-entry` on the business build.
    - **v1 limitations**: `stat()`-by-path on a `.patch` path still returns the on-disk *ciphertext* size; loaders that `fstat()` the opened fd see the correct plaintext size (memfd) and work. Relative `openat()` paths without a directory component are not redirected. Covered by `test_patch_shim` (decrypted read via shim + negative control: ciphertext without the shim).
    - **Env**: `ANTIREV_PATCH_LOG=<path>` — line-buffered log of every `open` decision, discovery lookup, and daemon fetch in `lrxd_<arch>.so`.
- **Preload-closure-deps on lazy fetch**: after receiving the closure, `dlopen_shim::fetch_closure` iterates it in topological (DFS post-order) order and calls `real_dlopen(symlink_path, RTLD_LAZY | RTLD_GLOBAL)` on every *non-root* entry before the caller's own `real_dlopen` of the root. `RTLD_GLOBAL` is mandatory — generated `.pb.cc` code exports `descriptor_table_<file>_2eproto` with default visibility, and duplicate definitions across plugins (common ODR-ish build pattern for protobuf) dedup via symbol interposition only when both DSOs are in the global scope. The root lib is explicitly skipped so the caller's own dlclose can actually unload it, which matters for plugin systems that cycle plugins carrying overlapping static state (see `test_dlopen_reload`, `test_dlopen_interpose`, `test_python_reload`).

### aarch64_extend_shim (aarch64-only)

Compiled into `antirev_shim.so` only on aarch64 (the source file is an empty TU on x86). Houses two unrelated aarch64-specific interceptors:

- **`ANTI_LoadProcess(struct ANTI_ProcessInfo *)` hijack**: business API that loads a program-binary `.elf` from the path in `info->ltrBin`. aarch64_extend_shim computes `basename(info->ltrBin)`, checks it against the shared `__r_EL` set (via `daemon_client_is_encrypted` — `.elf` and `.so` basenames coexist), and on match fetches the decrypted memfd from the daemon via **`OP_GET_LIB` (reused, no new opcode)**, rewrites `info->ltrBin = "/proc/self/fd/N"`, then calls the real `ANTI_LoadProcess` via `dlsym(RTLD_NEXT, ...)`. The rewrite is persistent — not restored on return — so deferred reads of `info->ltrBin` (worker threads, multi-stage loaders) still hit the memfd. `ANTI_UnLoadProcess(pgId)` is **not** intercepted — it keys on a pgId handle, not the path, and the kernel mapping created by the real `ANTI_LoadProcess` pins the memfd regardless of whether our fd cache stays open. The memfd fd is cached per pgName for the process lifetime.
- **`open` / `openat` / `stat` / `lstat` / `newfstatat` / `access`**: intercept the path-taking calls to redirect encrypted `.elf` assets (`maybe_rewrite_elf_path` → `/proc/self/fd/N`) for `ANTI_LoadProcess` paths that open by name. **Pass-through differs by call**: `openat` (and `open`, which calls it) chains the non-`.elf` case via **`dlsym(RTLD_NEXT, "openat")`** so a *later* `LD_PRELOAD` hook still gets it — critically, this lets `lrxd.so`'s `.pat` redirect coexist **regardless of `LD_PRELOAD` order** (both shims now chain, each handling its own suffix: `.pat`→lrxd, `.elf`→here, else→libc). The `stat`/`lstat`/`newfstatat`/`access` family instead pass through via **raw syscalls** (`raw_newfstatat`/`raw_faccessat`): `newfstatat`/`stat`/`lstat` are NOT exported libc symbols on glibc ≥ 2.33 (header inlines), so `dlsym(RTLD_NEXT, …)` returns NULL there → ENOSYS process-wide. That bug was stat-family-specific; `open`/`openat` are real exported symbols so they were reverted to `RTLD_NEXT` chaining (the raw-syscall sweep was guilt-by-association and broke `.pat` interop by not chaining). Consequence: `stat`-by-path on a `.pat` still hits ciphertext size (lrxd doesn't hook stat; this shim's raw stat reads disk) — fine for loaders that size via the opened fd (`fstat`/`ifstream::tellg`), see hot-patch v1 limitations.
- **`.pat` hot-patch redirect (aarch64 fallback, coexists with `lrxd.so`)**: besides `.elf`, the `open`/`openat` hooks **plus new `fopen`/`fopen64` hooks** detect a read-only open of a `.pat` in the owner process and fetch the decrypted memfd from the daemon via **`OP_GET_PATCH`** (`fetch_one` was refactored into `fetch_one_op(opcode, base)` — `.elf` keeps `OP_GET_LIB`, `.pat` uses `OP_GET_PATCH`; fresh memfd per open, no cache, like `lrxd.so`), returning it directly. This lets a **protected aarch64 process apply hot patches WITHOUT a separate `lrxd.so`**, reusing the existing `__r_LS` daemon connection (no discovery file, no extra preload). It **coexists with `lrxd.so`**: whichever shim sorts first in `LD_PRELOAD` handles the `.pat` and returns *without chaining*, so it is processed exactly once (`.elf` still only here). This is the aarch64 belt-and-suspenders that **removes the fragile "lrxd must precede antirev_shim" ordering requirement** — with lrxd → lrxd handles it; without lrxd or wrong order → antirev_shim handles it. The `fopen`/`fopen64` hooks are **mandatory**: glibc's `fopen*` open via a private internal open that bypasses the PLT, so an `ifstream`'s `fopen64(".pat")` would otherwise be missed. x86 still needs `lrxd.so` (this TU is empty there). **Maintenance note**: `.pat` suffix + fetch logic now lives in BOTH `patch_shim.c` (lrxd.so) and `aarch64_extend_shim.c` — keep them in sync (suffix, `OP_GET_PATCH` wire format, read-only gating).
- **`popen` / `pclose`**: moved verbatim from `exe_shim.c`. Rationale unchanged — glibc's vfork'd popen child corrupts the memfd-heavy parent; we override with plain fork+exec and maintain our own FILE*→pid table so `pclose` reaps the right child.

aarch64_extend_shim and `dlopen_shim` share the daemon socket via `daemon_client.c` — single `g_sock` for the whole DSO, accessed through `daemon_client_send` / `daemon_client_recv`. Both shims have their own mutex, so cross-shim requests hitting the socket concurrently from different threads could interleave responses — not an issue today because `ANTI_LoadProcess` is called at process init (single-threaded) while `dlopen` happens later, but worth noting if that timing ever changes.

Packing:

- **CLI path** (`protect-daemon --libs`): `.elf` files can be passed alongside `.so` files — daemon indexes them by basename, no separate flag.
- **YAML/`antirev-pack.py` path**: `classify_elf` treats any file whose basename ends in `.elf` as `kind='lib'` (regardless of ET_EXEC vs ET_DYN), so `.elf` PG binaries flow through the same encrypt/skip + `encrypt_libs` / `plaintext_libs` filters as `.so` libs. Without this, ET_EXEC `.elf` files would fall into the exe pipeline and get wrapped as standalone `.protected` stubs — wrong semantics for ANTI_LoadProcess targets. `_encrypt_lib_worker` skips the patchelf SONAME-patching step for `.elf` files (ANTI_LoadProcess targets are looked up by basename via `OP_GET_LIB`, never via DT_NEEDED, so no SONAME is needed).
- **Stub side**: `scan_encrypted_libs` in `stub.c` accepts both `.so` and `.elf` extensions as its fast-path filename filter — the authoritative check remains the `ANTREV01` magic header.
- **Unsupported-arch fallback**: when the YAML `stubs:` map omits an arch present in the install tree (e.g. only `aarch64` configured but x86_64 binaries appear), `antirev-pack.py` no longer hard-errors. The unmatched ELFs are copied to `output_dir` as plaintext with a per-arch `[pack] WARNING` summary listing each affected file. This keeps the install tree complete while flagging the omission so a typo in `stubs:` is still visible.

### aarch64_extend_shim env vars (runtime)

- `ANTIREV_AARCH64_EXTEND_LOG=<path>` — line-buffered log of every `ANTI_LoadProcess` call, path-rewrite decision, and daemon fetch outcome. Use this to diagnose "daemon returned no fd" or "basename not in enc list" issues in the field.

### dlopen_shim env vars (runtime)

- `ANTIREV_DLOPEN_LOG=<path>` — when set, `dlopen_shim` writes every `dlopen` decision, closure fetch, preload, and failure to `<path>` with line-buffered IO. Required for diagnosing any closure / preload issue in the field.
- `__r_NP=1` — escape hatch that disables the per-dep preload loop entirely. `fetch_closure` still fetches the closure and materializes symlinks, but the caller's `real_dlopen(root)` then triggers glibc's normal recursive DT_NEEDED walk, which maps every dep first and runs all ctors together at the end — matching plaintext semantics exactly. Use this for apps with **implicit inter-lib symbol dependencies**, where one business lib references a symbol provided by a sibling lib without an explicit `DT_NEEDED` edge (e.g. `_ZN3BBBC1EPN6google8protobuf5ArenaE` — `BBB::BBB(google::protobuf::Arena*)` — needed by libccc but provided by libbbb with no edge between them). The per-dep preload loop loads ctors in isolation and can trip lazy-binding failures across the implicit boundary; natural load sidesteps it. Tradeoff: without preload, any lib whose `DT_RPATH` points at the encrypted on-disk dir will have its own DT_NEEDED search hit ciphertext before `LD_LIBRARY_PATH` catches it — so `__r_NP` is opt-in per-app, set in the start script, not the default. The correct long-term fix is to add the missing `DT_NEEDED` edge to the business build (`target_link_libraries(CCC PRIVATE BBB)` in libccc's CMakeLists), which makes the dependency explicit and works for every loader.

### Python integration

Python scripts load encrypted libs via `antirev_client.py` — called from within Python (`from antirev_client import activate`). Connects to the daemon, patches `ctypes.CDLL` and `sys.meta_path` to redirect to memfd-backed libs. Loads encrypted libs with `RTLD_GLOBAL` and creates soname symlinks in a temp dir prepended to `LD_LIBRARY_PATH`. Speaks daemon protocol v2 — sends `OP_INIT` on connect and collects `OP_BATCH`/`OP_END` framed replies. Covered by `test_python_client_daemon`.

### Known issues with memfd loading

- Each decrypted lib holds an open memfd, consuming file descriptors. Large deployments (550+ libs) may require raising `ulimit -n`.
- The dynamic linker's path-based deduplication uses `l_name` from the load path. The same library accessed via memfd path (`/proc/self/fd/N`) vs disk path may be treated as different libraries.
- **Duplicate-symbol detection**: `tools/missing_syms.py` runs a per-target duplicate-symbol scan by default. For every project ELF it walks the transitive DT_NEEDED closure (plus the ELF itself) and reports symbols defined by more than one DSO in that load image. STRONG-vs-STRONG duplicates are errors (real interposition / ODR risk); WEAK-vs-WEAK and STRONG-vs-WEAK are warnings (common C++ vague linkage; usually benign but worth surfacing). C++ vague-linkage prefixes (`_ZTV`, `_ZTI`, `_ZTS`, `_ZTC`, `_ZTT`) are filtered by default — pass `--all-cxx` to include them. System-lib-only duplicates (e.g. libc vs ld-linux) are filtered unless `--system-dups` is given. Use `--no-duplicates` to skip this pass.
- Legacy binaries without the needed-section (backward compat) still use LD_PRELOAD for encrypted libs, which changes symbol lookup order. Re-pack with `antirev-pack.py` to get the symlink-dir-only approach.
- **Debug symbol files (.debug) affect runtime behavior**: exe_shim spoofs `readlink("/proc/self/exe")` to point to the encrypted stub on disk. Business software that scans for `.debug` files relative to the exe path (e.g., signal handlers, crash recovery) will find or miss them depending on deployment. Two encrypted processes (Foo, Bar) crash in open62541 `ua_client()` init when `.debug` files are absent, but work fine when present. A standalone demo (tests/opcua_enc/) confirmed encryption itself does NOT cause the crash — the issue is the business software's debug-file-dependent infrastructure. **Workaround**: always deploy `.debug` files alongside encrypted binaries. **Investigation pending**: strace to identify which library reads `.debug` at runtime.

## kmod2: antirevfs kernel module (experimental alternative architecture)

`kmod2/` is a self-contained, alternative architecture (see `kmod2/DESIGN.md`) that replaces the entire stub + shim + daemon + `antirev_client.py` stack with a stacked read-only kernel filesystem, **`antirevfs`**. It is NOT wired into the main CMake build or `run_all_tests.cmake` — it has its own kbuild Makefile and a standalone root-only test. It is a working PoC/v1, not the production path; the daemon/shim architecture above is still the shipping design.

- **What it does**: ciphertext lives under a lower `.enc/` tree; antirevfs mounts over it and decrypts `ANTREV01` AES-256-GCM files in `read_folio` (page-fault servicing). The kernel page cache gives cross-process page sharing for free — no daemon, no `LD_PRELOAD`, no `memfd:` artifact in `/proc/<pid>/maps`. glibc/`ld.so`/Python see plaintext at real paths, so the implicit-DT_NEEDED / ODR pain (`ANTIREV_NO_PRELOAD`) disappears with native symbol resolution.
- **On-disk format reused unchanged**: `encryptor/protect.py encrypt-lib` output — `[magic ANTREV01:8][iv:12][tag:16][ct...]`. Whole plaintext is one GCM message; `read_folio` does a one-shot whole-file decrypt into a per-inode buffer on first fault (tag verified once), then serves pages from it. Per-page random decrypt is impossible because GCM authenticates the entire message.
- **Module sources** (`kmod2/module/`): `super.c` (fs registration, `mount_nodev`, option parse, key acquisition, inode/sb lifecycle), `inode.c` (lookup proxied to lower tree, `iget5_locked` caching keyed on lower dentry so one antirevfs inode == one shared page cache per path, getattr reporting plaintext size, and **symlink support** — `S_IFLNK` lower inodes get an `antirevfs_symlink_iops` whose `get_link` proxies to the lower link via `vfs_get_link`, so packer-mirrored SONAME chains / version links resolve through the mount; without this the module rejected every symlink with `-EINVAL` and they showed as `l?????????` / dangling), `file.c` (`read_folio` decrypt-on-fault, dir `iterate_shared`, generic file ops + `generic_file_mmap`), `crypto.c` (`gcm(aes)` via kernel crypto API; file layout has tag *before* ct, so it builds a `[ct||tag]` buffer for the AEAD), `antirevfs.h`.
- **Strict mode + passthrough + passdata**: a file under the mount lacking `ANTREV01` magic returns `-EIO` unless either (a) its extension is in the mount's `passthrough=` whitelist (colon-separated, since `,` separates mount options), or (b) the mount carries the `passdata` option, which serves **any** non-`ANTREV01` file as plaintext passthrough. Decided at inode-classify time (open of lower file to sniff magic). `passdata` is the mode for a **complete mixed-content read-only tree** (a real `lib/`/`bin/` holding encrypted ELFs *plus* `.py`/`.pyc`/`.sh`/`.txt`/`.json` data files *plus* third-party plaintext ELFs that coexist) — produced by `antirev-fs-pack.py` with `mirror_plaintext`. Encrypted (`ANTREV01`) files are still decrypted and gated as usual; only non-magic files become plaintext. Tradeoff vs the extension whitelist: `passdata` drops strict mode's "an unencrypted ELF that slipped past the packer is loud" net (a forgotten-to-encrypt `.so` would be served plaintext), so it relies on the packer's encrypt-all-ELF default + manifest review. The mount stays **read-only**: any file the app *writes* at runtime (python-generated `.txt`, `__pycache__`) must be redirected to a writable path outside the mount — antirevfs hosts only shipped content, and edits to `bin/`/`lib/` are intentionally impossible. Mount via `antirev-mount --passdata <lower> <mp>`.
- **Key**: looked up via `request_key("user", "antirevfs:default")` from the mount path, which searches the mounting task's **session keyring** — so `antirev-keyctl unlock` and `mount` must run in the same session (`sudo`/`pam_keyinit` gives a fresh session keyring that doesn't link `@u`). `key=<64hex>` mount option is the test/fstab escape hatch. The mount-resident key is wiped (`memzero_explicit`) on unmount.
    - **Session-keyring gotcha (must share a real `_ses`)**: `request_key()` runs in the *mount process's* context, so the key must live in a session keyring that process inherits. If the invoking shell has **no session keyring of its own** (a root shell from SLES `su`, ssh/cron, etc. — no `pam_keyinit`), then `keyctl padd @s` creates an *ephemeral* session keyring local to the `keyctl` process; it vanishes before `mount` runs, so `request_key()` returns `-ENOKEY` and every read fails with "Required key not available". A login shell that already owns a `_ses` (a desktop dev box) masks the bug — which is why it passed on 6.8.0-117 but failed on SLES 12 SP5. `test_antirevfs.sh` now `exec`s itself under a fresh `keyctl session -` so `keyctl` and `mount` share one real `_ses` regardless of the starting environment; production deployments must do the same (run unlock + mount inside one `keyctl session …` / systemd unit, or use the `key=` mount option in fstab).
- **Tools** (`kmod2/tools/`): `antirev-keyctl` (add/clear key in `@s`), `antirev-mount` (`mount -t antirevfs` wrapper). `dkms.conf` for auto-rebuild on kernel upgrade.
- **Packer** (`kmod2/tools/antirev-fs-pack.py <config.yaml>`): the antirevfs-side analog of `encryptor/antirev-pack.py`. Where `antirev-pack.py` builds stub/daemon/shim artifacts, this tool produces the **ciphertext lower tree** antirevfs mounts over. It walks `install_dir`, encrypts **every ELF** (shared libs AND executables — detected by `\x7fELF` magic, not extension) into a mirrored `output_dir/` tree via `protect.py`'s exact `encrypt-lib` container (reuses `MAGIC`/`encrypt_data`/`load_or_create_key` so the format stays in lockstep with `read_folio`), and writes a JSON manifest *outside* the tree. Config fields: `install_dir`, `output_dir`, `key` (hex keyfile relative to the config, created 0600 if absent), optional `blacklist` (basename globs like `libprotobuf.so*`, or `prefix/` path subtrees — left UNencrypted for third-party libs that coexist plaintext), optional `mirror_plaintext` (default **true**). **`mirror_plaintext` (default) produces a COMPLETE mixed-content tree**: ELFs are encrypted; every other regular file (`.py`/`.pyc`/`.sh`/`.txt`/`.json`/resources) **and** blacklisted (intentionally-plaintext third-party) ELFs are **mirrored verbatim (plaintext) into the tree** (via `copy_verbatim`), and symlinks re-created — so a real `lib/`/`bin/` appears in full under a `passdata` mount. Set `mirror_plaintext: false` for a minimal pure-secret tree (only encrypted ELFs + symlinks land in the tree; data files and blacklisted ELFs are omitted and will NOT appear under the mount — point it at pure-ELF subtrees). The manifest gains a `plaintext` list (mirrored files) alongside `encrypted`/`symlinks`. **Symlinks are mirrored verbatim** so SONAME version chains (`libfoo.so → .so.1 → .so.1.2.3`) keep resolving through the mount. Because the mount is read-only, runtime-written files (python `.txt`, `__pycache__`) must be redirected to a writable path outside the mount. Prints suggested `keyctl session -`-wrapped mount commands per subtree (with `antirev-mount --passdata` when mirroring). `--dry-run` classifies without writing. Covered by `kmod2/tests/test_fs_pack.sh` (userspace, no root: ELF detect, mirror layout, ciphertext/decrypt round-trip, non-ELF + blacklisted-ELF mirrored plaintext, symlink preservation, manifest `plaintext` list, `mirror_plaintext:false` minimal tree) and the `passdata` section of `kmod2/tests/test_antirevfs.sh` (encrypted lib still decrypts; third-party plaintext ELF + unlisted-extension script served verbatim).
- **Kernel compat**: `compat.h` + inline `LINUX_VERSION_CODE` guards span mainline 6.8 down to **SLES 12 / 4.12.14-default** (the real x86_64 deployment target). Guarded APIs: `read_folio`↔`readpage` (5.18), crypto async-wait trio `DECLARE_CRYPTO_WAIT`/`crypto_req_done`/`crypto_wait_req` (4.16; hand-rolled completion below that), `getattr`/`generic_fillattr` signature bands (5.12/6.3/6.6), `alloc_inode_sb` (5.17), `free_inode`↔`destroy_inode`+`call_rcu` (5.2), `kernel_read` signature (4.14, via `arev_kernel_read`), `SB_*`↔`MS_*` flags (4.15), `hex.h` split (5.18), `get_mm_exe_file` export gap (Ubuntu's 6.8 generic build drops the `EXPORT_SYMBOL` that SLES 4.12 keeps; open-coded via the always-exported `get_file_rcu` in `arev_get_mm_exe_file`, with a 6.7 `get_file_rcu` signature guard), exec-load detection (`FMODE_EXEC` in `f_mode` on 4.12 vs `__FMODE_EXEC` in `f_flags` on 6.8 where `FMODE_EXEC` is clear at `->open` — both homes tested by `arev_is_exec_open`). Enterprise kernels backport APIs while keeping an old version code — override macros like `-DAREV_NEW_KERNEL_READ` handle the mismatch. **Both ends now runtime-verified**: mainline 6.8.0-117 / 6.8.0-124 *and* SLES 12 SP5 (`4.12.14-120-default`), including the decrypt-authorization gate (on stock mainline 6.8 the gate needs the `arev_get_mm_exe_file` + `arev_is_exec_open` compat shims above — without them modpost fails on `get_mm_exe_file` and listed encrypted executables are wrongly denied). On SLES, build with the kernel's own gcc major version — the kernel ships built with gcc 4.8.5, so `make CC=gcc-4.8` even though the distro default `gcc` may be 9.x (a 4.8→9 jump trips stricter-diagnostic build errors; module loading is gated by vermagic = kernel release, not the compiler version).
- **Build/test**: compile with the kernel's own compiler major version — `make -C kmod2/module CC=gcc-12` on the 6.8 dev box, `make CC=gcc-4.8` (after `zypper install kernel-default-devel gcc48`) on SLES 12 SP5. End-to-end: `sudo bash kmod2/tests/test_antirevfs.sh` (18 checks: decrypt correctness, ciphertext-on-disk, dlopen through mount, real path / no memfd in maps, strict-mode reject, `passthrough=` whitelist, wrong-key rejection, cross-process PFN sharing, a `passdata` mixed-content section — encrypted lib still decrypts while a third-party plaintext ELF and an unlisted-extension script are served verbatim — and a **symlink section**: `readlink` through the mount, a chain to an encrypted lib that decrypts, a link to a passthrough data file, and a genuinely-broken link that correctly dangles) , `sudo bash kmod2/tests/test_gate.sh` (decrypt-authorization gate: authorized read, cp/cat denied, identity-not-action, execve lifecycle, listed encrypted exe runs while `cp` of it is denied, enforce-toggle control), `sudo bash kmod2/tests/test_gate_whitelist.sh` (multi-program whitelist at the documented default `/etc/authorized_apps.txt`: every listed encrypted program runs, an unlisted "undocumented" encrypted program is refused execution, `cp`/`cat` denied), and `sudo bash kmod2/tests/test_gate_access_matrix.sh` (explicit `{execute, read, write} × {listed, unlisted}` matrix: listed exe executes / unlisted refused; `cat`/`cp` read denied for both — no exfiltration; **write denied for both because the mount is read-only**, proven independent of the gate via the `gate_enforce=0` control where execute+read flip but write still fails; plus the meaningful cell — a process *running as* the listed exe successfully reads an encrypted data file while `cat` cannot). Runtime-validated on kernel 6.8.0-117 / 6.8.0-124 **and** SLES 12 SP5 `4.12.14-120-default`. Resolves DESIGN.md open question #8.
- **Threat model + the decrypt-on-read leak (data-in-use boundary)**: antirevfs protects **data at rest**, not **data in use** — the mount point is a real path that hands plaintext to *any* reader, so `cp /proj/lib/foo.so /usb/` exfiltrates a clean plaintext ELF (the `.enc/` lower tree is ciphertext and safe to copy; the **mount view** is the leak). This is the #1 vector to reason about, and it's judged against a **two-tier adversary**:
    - **At-box adversary = the client** — physically owns HW+SW but is a *non-technical operator* (GUI buttons, drag-and-drop, copy-to-USB; no concept of root, mount namespaces, decryption, or memory forensics). Attack: "copy the software folder and hand it to someone."
    - **Capable adversary = the competitor** — expert reverse-engineers, but **decoupled from the live appliance**; they only ever receive the bits the rookie copied, never root on a running box (no `nsenter`/`gcore`/page-cache dump).
    - **Consequence**: the whole problem reduces to *"what a non-technical user can copy via GUI/USB must be ciphertext."* Sophisticated-root attacks are genuinely out of scope — the at-box person can't do them and the person who can isn't at the box. (This corrects an earlier framing that treated the at-box adversary as root-capable.)
    - **Primary mitigation — namespace-isolate the plaintext mount**: launch the business app via a wrapper that `unshare -m`s (or a systemd unit with `PrivateMounts=yes`) and mounts antirevfs *inside* that namespace, so a normal GUI/file-manager session sees only the `.enc/` ciphertext tree — there is no plaintext path for the rookie to navigate to. Under this threat model isolation is **sufficient, not theater**: the rookie can't bypass it (doesn't know namespaces exist) and the competitor never reaches the box to `nsenter`. A whole-disk/USB copy captures only `.enc/` + the `.ko` + the TPM-sealed key blob.
    - **Backstop — TPM per-unit sealed key** (see deployment/key-mgmt notes): makes any exfiltrated ciphertext doubly useless — the competitor can't decrypt it (key never left the box) and can't even run it on other hardware (key won't unseal against a different TPM/PCRs).
    - **Boundary case — coached rookie**: a rookie talked through `nsenter`/`cp` over the phone escalates toward competitor-at-box. Optional belt-and-suspenders: **PROT_EXEC-gated decryption in `read_folio`** (serve plaintext only to executable faults; plain `read()`/`cp` → ciphertext or `-EIO`) defeats even a coached `cp`, leaving only a hard-to-coach memory dump. Not required for the solo-rookie case; must be done carefully so `ld.so`'s non-exec header/`.rodata` reads still load.
    - **Fundamental limit**: the CPU executes plaintext, so plaintext is in RAM, so ring-0/root can always read it — no kernel-FS trick (nor the memfd design) beats that. Only hardware memory encryption (SEV-SNP / TDX / enclaves) changes the theorem; out of scope given the adversary model above.
- **Decrypt-authorization gate (`module/gate.c`)**: per-process gating so only an *authorized* process can open an encrypted file and reach plaintext via the shared page cache; `cp`/backups/file-managers get `-EACCES` and can only ever read the lower `.enc/` ciphertext. Policy lives behind two seams in `antirevfs_file_open()`, applied *only to encrypted files* (`ii->encrypted`), enforcing with `-EACCES`. Gating at **open** (before any read/mmap/splice) is what lets the business app load natively through the shared plaintext cache while everyone else is denied — it does not duplicate physical pages (authorized openers share one cache; unauthorized never open).
    - **Exec-load vs data-read use different identities (critical):** at `execve`, the kernel opens the program *before* `current->mm->exe_file` becomes that program — it's still the caller (the shell) — so gating an exec-load on the caller's exe would deny **every** encrypted executable (catch-22: the binary can't authorize its own launch). So `antirevfs_file_open()` splits on exec-intent (`arev_is_exec_open()` — `FMODE_EXEC` in `f_mode` on 4.12, `__FMODE_EXEC` in `f_flags` on mainline 6.8 where `FMODE_EXEC` is clear at `->open`; `current->in_execve` is NOT usable here because the kernel opens the binary in `alloc_bprm()` before `bprm_execve()` sets it): an **exec-load** is gated by `antirevfs_file_authorized(file)` on the **program's OWN path** (running a program is not a plaintext-file exfiltration vector — bytes land only in the new process's executable mapping); **every other open** (lib loads, `cp`, `source`) is gated by `antirevfs_task_authorized()` on the **calling process's exe** (`current->mm->exe_file`), which is what keeps `cp` on ciphertext. So a listed binary runs *and* its lib loads pass (running exe == listed), while `cp` of that same binary is denied.
    - Data-read lifecycle is free: `current->mm->exe_file` is updated by the kernel at `execve`, so **`fork()` inherits authorization and `execve()` of an unlisted helper (e.g. an authorized app shelling out to `/bin/cp`) drops it** with no task bookkeeping.
    - **Step 1 (implemented)** — `authz_exe_allowed()` resolves `current`'s exe path (`arev_get_mm_exe_file` + `d_path`) and matches it against a newline-separated allow-list file (module params: `gate_enforce` bool default 0 = allow-all so existing tests are unaffected; `authz_path` default `/etc/authorized_apps.txt`). An entry with `/` matches the full path, without `/` matches the basename; `#` comments and blanks ignored; re-read per-open so the list can be edited live. This is a **correctness demonstrator, not a security boundary** — anyone who can write the allow-list or place a binary at an allowed path passes. The allow-list is opened with the caller's creds, so it must be readable by the business processes (e.g. 0644). Covered by `kmod2/tests/test_gate.sh` (authorized read allowed; `cp`/`cat` denied; byte-identical-but-unlisted loader denied → gates on *identity* not action; authorized parent's `cp` child denied → execve lifecycle; `gate_enforce=0` control proves the gate is the enforcer; lower file still ciphertext).
    - **Step 2 (planned, one-function swap)** — replace only the body of `authz_exe_allowed()` with a signature check: verify `current->mm->exe_file`'s detached signature (xattr/trailer) against a public key in a **locked kernel keyring**, anchored in **TPM measured boot** (a tampered kernel won't unseal the AES key, so it can't bypass the gate). The call site, `-EACCES` enforcement, encrypted-only scoping, fork/execve lifecycle, and shared-cache behaviour are unchanged. This is the version that does **not** depend on the operator being unprivileged. Optionally move the verdict to an exec-time LSM `bprm_check_security` hook + task flag for caching, but that's a perf optimization, not required for correctness.
- **Not yet done**: module signing for Secure Boot, key rotation, DKMS `.deb`/`.rpm` packaging, gate step 2 (signature-based authorization).
